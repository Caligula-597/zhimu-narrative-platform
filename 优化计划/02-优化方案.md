## 一、架构优化

### A1. 主应用模块化迁移（P0，最高优先级）

**目标**：把根 `src/` 从 `window.* + IIFE` 迁移到真 ES Modules，与 `play/host` 一致。

**迁移策略：渐进式、按视图逐个迁、不中断业务**

迁移单元是**视图文件**（`src/views/*.js`）和**运行时模块**（`src/runtime/*.js`）。每个单元独立迁移、独立验证，不必一次性全改。

**单文件迁移模板**：

迁移前（现状）：
```js
(function (window) {
  const state = window.zhimuState;
  const zhimuApi = window.zhimuApi;
  const { content, toast } = window.zhimuDom;
  const F = window.zhimuFormat || {};
  const escapeHtml = F.escapeHtml || ((v="") => String(v));
  // ...20 行别名...
  window.zhimuViews = window.zhimuViews || {};
  window.zhimuViews.overview = window.zhimuViews.overview || {};
  function overview() { /* ... */ }
  window.zhimuViews.overview.overview = overview;
})(window);
export {};
```

迁移后（目标）：
```js
import { state } from "../state.js";
import { api } from "../api/client.js";
import { content, toast } from "../dom.js";
import { escapeHtml, formatTime } from "../utils/format.js";
// ...显式 import...

export function overview() { /* ... */ }
```

**关键步骤**：

1. **先迁基础层**（无依赖的叶子模块）：
   - `src/utils/format.js` → 真 export
   - `src/utils/user-messages.js` → 真 export
   - `src/dom.js` → 真 export
   - `src/state.js` → 真 export（见 A2）

2. **再迁 API 层**（见 A3）

3. **再迁 runtime 层**：`session-auth.js`、`auth-session.js`、`nav-shell.js`、`view-loader.js`、`data.js`、`actions-*.js`...

4. **最后迁 views 层**：每个 view 独立迁，迁完一个跑一次 `npm run build` + `npm run check:modules`

5. `frontend/main.js` 的 import 列表逐步缩短，最后只剩入口 `app.js`

6. `app.js` 自身改为真 export：`export function render() {}`、`export function go(view) {}`，删除 `window.zhimuRuntime = Object.assign(...)` 拼接

**验证命令**（每个单元迁完都跑）：
```powershell
npm run check:modules   # 验证脚本加载
npm run build           # 验证构建
npm run test:e2e -- --project=chromium  # 验证关键路径
```

**风险与对策**：
- 风险：迁移中两种模式并存可能导致 `window.zhimuXxx` 未定义。
- 对策：保留 `window.zhimuXxx` 作为**临时桥接**，迁移完成的模块同时 `export` 真值并赋给 `window.zhimuXxx`，全部迁完后再删 `window.*` 赋值。

### A2. 状态分片（P0）

**目标**：把 `zhimuState` 60+ 平铺属性拆成 6-8 个领域 store，每个 store 独立可订阅。

**分片方案**：

```
src/state/
├── index.js              ← 聚合 export，兼容旧代码
├── user-store.js         ← currentUser, apiError, roomEventsConnected
├── world-store.js        ← cloudWorlds, cloudCatalog, cloudStudio, cloudCreatorChecks
├── room-store.js         ← cloudHost, cloudHostPlayers, cloudHostEvents, cloudCheckpoints, cloudRecaps...
├── studio-store.js       ← studioSelectedNode, studioFilter, studioZoom, studioLayoutMode...
├── asset-store.js        ← cloudAssets, assetKindFilter, assetSearchQuery, assetShowRecycle
├── voice-store.js        ← voiceRoom, voiceMessages, voiceLiveStatus, voiceMicEnabled...
├── wizard-store.js       ← wizardStep, wizardDraft, wizardRoleEditor
└── ui-store.js           ← view, panelCollapse, accountHubTab, searchFocus, cluesSearchQuery
```

**轻量订阅模式**（不引入库）：

```js
// src/state/create-store.js
export function createStore(initial) {
  let state = { ...initial };
  const listeners = new Set();
  return {
    get: () => state,
    set: (patch) => {
      const prev = state;
      state = { ...state, ...patch };
      listeners.forEach((fn) => fn(state, prev));
    },
    subscribe: (fn) => { listeners.add(fn); return () => listeners.delete(fn); }
  };
}
```

**兼容桥**：`src/state/index.js` 仍导出 `zhimuState` 对象（getter 聚合各 store），让未迁移的旧代码继续工作。

## 二、性能优化

### P1. 主应用渲染：从全量 innerHTML 到局部 patch

**目标**：借鉴 play 的 `patchSyncChrome` 模式，大视图（studio、clues、host events）改为局部更新。

**方案**：
- 保留 `render()` 作为全量入口
- 在 `app.js` 的 `setContentHtml` 之上加一层 `patchChrome(state, prev)`：
  - 比较 `state.view`、`state.cloudLoading`、`state.apiError` 等外壳字段
  - 仅外壳变更时 patch 顶部/侧边栏/状态条，不重渲 content
- 大视图内部：滚动位置、输入焦点在 `render()` 前后保存恢复（play 已有此模式）

**收益**：studio 图谱拖拽、clues 搜索过滤不再触发全量重渲。

### P2. API 客户端缓存

**目标**：减少重复 GET，尤其是不变的 world/studio 数据。

**方案**：在 `api/client.js` 的 `request()` 上加可选缓存层：

```js
const cache = new Map();
function cachedGet(path, ttl = 30_000) {
  const hit = cache.get(path);
  if (hit && Date.now() - hit.t < ttl) return Promise.resolve(hit.v);
  return request(path).then((v) => { cache.set(path, { t: Date.now(), v }); return v; });
}
```

- `worlds/list`、`studio/graph`、`catalog` 等读多写少接口走缓存
- 写操作（POST/PATCH/DELETE）自动 invalidate 对应 key
- 提供 `api.invalidate(pattern)` 手动失效

### P3. 骨架屏

**目标**：消除"切视图白屏"和"进监控台卡顿"的感知。

**方案**：
- 主应用 `view-loader` 等待期已有 `renderViewLoading`，把它升级为**骨架屏**（占位卡片轮廓 + shimmer 动画）
- host 监控台进入时，先渲染 console 壳 + 各面板骨架，数据到了再填
- play 端 `pullRoomData` 期间，game 视图保留旧数据 + 顶部细 loading（已有）

### P4. 资源加载

- 三端共用的 `zhimu-product-hero.png` 移到 `shared/assets/`，避免三份引用
- 字体考虑自托管（CSP font-src 已放行 `data:`），减少对 Google Fonts CDN 依赖
- Vite build 已开 sourcemap，生产可保留（便于内测期排错）

### P5. 后端聚合 API（P1，详见 D1）

主应用 overview 视图当前要并发 4-6 个请求拼数据。后端补一个 `/api/creator/overview` 聚合接口，一次返回世界健康度 + 下一步建议 + 最近工作 + 三端入口状态。
