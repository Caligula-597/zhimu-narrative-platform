## 一、架构现状

### 1.1 整体拓扑

```
Cloudflare Pages             Railway fullstack                 Cloudflare Pages
getzhimu.com                 app.getzhimu.com                  play.getzhimu.com
site/ 官网                   根目录主应用 + /api               play/ 玩家端

                              PostgreSQL · R2 · OTLP · alerts · metrics

Cloudflare Pages
host.getzhimu.com
host/ 主持端
```

- 后端：Fastify 5，44 个 SQL migrations，40+ 路由模块，单一真相源
- 前端：4 个独立 Vite 应用，共享层仅 `shared/tokens.css`

### 1.2 主应用架构问题（核心痛点）

主应用（根目录 `src/`）是项目最早期的代码，至今仍是**伪 ES 模块**模式：

**问题 1：`frontend/main.js` 只是 import 顺序清单**

文件本身就是 44 行 import 列表，注释明确写着「import order mirrors legacy index.html script chain」。每个被 import 的模块实际上仍通过 `window.*` 挂载互相通信，ES import 在这里只起到排序作用，没有真正利用模块边界。

**问题 2：`window.*` 全局命名空间 + IIFE 包装**

每个模块都是 `(function(window){ ... })(window); export {};` 形态：
- 用 IIFE 包裹是为了不污染全局
- 但又把所有 API 挂到 `window.zhimuXxx`
- `export {}` 是空导出，仅为了让 Vite 当模块处理

这导致：模块间依赖关系隐式（靠 `window.zhimuXxx` 运行时查找），Tree-shaking 失效，IDE 跳转/类型推断失效。

**问题 3：`zhimuState` 60+ 属性平铺**

`src/state.js` 109 行，单个 `window.zhimuState` 对象混合了：
- 用户/会话（`currentUser`、`apiError`）
- 云端数据（`cloudWorlds`、`cloudHost`、`cloudStudio`、`cloudAssets`...）
- UI 视图状态（`view`、`studioFilter`、`studioZoom`、`panelCollapse`...）
- 语音（`voiceRoom`、`voiceMessages`、`voiceMicEnabled`...）
- 向导草稿（`wizardStep`、`wizardDraft` 嵌套三套 roleSets/contentSets）

没有分片、没有订阅机制。任何状态变更都靠 `window.zhimuRender()` 全量重渲。

**问题 4：`api/client.js` 599 行单体**

单个 `window.zhimuApi` 对象包含 100+ 方法，混合所有领域：world、room、host、player、asset、ai、ops、auth、billing、clue、recap、checkpoint、voice... 无缓存层、无请求去重、无 SWR。

**问题 5：视图文件依赖拉取冗长**

每个 `src/views/*.js` 顶部都是 20+ 行 `const X = window.zhimuXxx || {}` 别名拉取，重复且脆弱（任一别名缺失就静默失败）。

### 1.3 三端前端架构（play/host/site）

相比之下，`play/`、`host/`、`site/` 已经是**真正的 ES Modules**：

- `import { api, state, setToast } from "./..."` 真实导出
- 每端有自己的 `api.js`、`state.js`、`security.js`、`errors.js`、`styles.css`
- 结构清晰，可读性好

**但存在严重的三端重复**：

| 重复模块 | play/ | host/ | 主应用 |
|---|---|---|---|
| API 客户端 | `src/api.js` | `src/api.js` | `src/api/client.js`（599 行） |
| 状态 | `src/state.js` | `src/state.js` | `src/state.js`（全局） |
| 安全工具 | `src/security.js` | `src/security.js` | 散落在各处 |
| 错误处理 | `src/errors.js` | `src/errors.js` | `src/utils/user-messages.js` + `src/api/errors.js` |
| OAuth 跳转校验 | `isSafeOAuthRedirectUrl` | `isSafeOAuthRedirectUrl` | 主应用未集中 |
| escapeHtml | `security.js` | 各 view 内联 | `utils/format.js` |
| isUuid | `security.js` | `security.js` | 主应用未集中 |

修一个 bug 要改三处，是当前最现实的工程风险。

### 1.4 后端架构

后端结构健康，**不需要大改**：

- `backend/src/app.js`：Fastify 实例、CORS、安全头、限流、统一错误、metrics
- `backend/src/server.js`：启动校验、OpenTelemetry、事件总线、告警 monitor、优雅关闭
- `backend/src/routes/`：40+ 按领域拆分的路由文件
- `backend/src/prompts/`：DeepSeek 多阶段创作 pipeline
- `backend/src/auth.js` + `session-cookie.js`：Session、guest、HttpOnly cookie

**值得注意的"后端超前于前端"**：
- migration `044_knowledge_chunks.sql` 知识块检索已落地，前端尚未产品化
- `world-revision.js` 内容版本冲突已有底座，前端协同编辑 UI 未跟上
- `story-assistant-routes.js` DeepSeek pipeline 后端完整，前端创作台未充分暴露

### 1.5 共享层现状

```
shared/
└── tokens.css   ← 仅此一个
```

设计 token 已共享（颜色、字体、圆角、阴影、内容宽度），但**逻辑层零共享**。

## 二、代码写法现状

### 2.1 主应用：IIFE + Object.assign 拼接

```js
// 典型模式
(function (window) {
  const state = window.zhimuState;
  const zhimuApi = window.zhimuApi;
  // ...20 行别名拉取...
  window.zhimuViews = window.zhimuViews || {};
  window.zhimuViews.overview = window.zhimuViews.overview || {};
  // 业务逻辑挂到 window.zhimuViews.overview
})(window);
export {};
```

```js
// app.js 末尾的拼接
window.zhimuRuntime = Object.assign(window.zhimuRuntime || {}, { render, go });
```

**问题**：
- 模块边界形同虚设
- `Object.assign` 拼接方法无法被 IDE 正确推断
- 新增方法靠"挂到 window"，没有显式 export 列表
- 删除方法后不会有"未使用"警告

### 2.2 三端：真 ES Modules

```js
// play/src/main.js
import { api, clearSession, getPlayOrigin, getSessionToken, setSessionToken } from "./api.js";
import { ALLOWED_OAUTH_PROVIDERS, isSafeOAuthRedirectUrl, isUuid } from "./security.js";
```

清晰、可跳转、可 Tree-shake。这是主应用应当对齐的目标。

### 2.3 innerHTML 使用密度

`src/` 下 17 个文件共 102 处 `innerHTML` 赋值（已用 `scripts/audit-innerhtml.mjs` 常态化审计）。在 CSP enforce 下基本安全（script-src 'self'），但仍需持续关注：
- 是否所有动态插值都经过 `escapeHtml`
- 是否有 `data-*` 属性被未转义插入

### 2.4 命名与分层

- 后端命名规范一致（`registerXxxRoutes`、`xxx-helpers.js`、`xxx-routes.js`）
- 前端三端命名也规范（`views/`、`runtime/`、`components/`、`utils/`）
- 主应用因历史原因，`runtime/` 下混了 store、actions、coordinator 多种职责

## 三、运行加载速度现状

### 3.1 已修复的性能问题

`docs/performance/PENDING_ISSUES_ZH.md` 记录了两项已修复的 host 卡顿：
- 进入监控台卡顿：视图切换前移 + 加载态先渲染
- 手动操作卡顿：`loadHostData()` 全量刷新改为粒度刷新（`refreshHostRoom/Players/ClueMatrix`）

修复模式值得在主应用复用。

### 3.2 主应用渲染策略

```js
// app.js
let lastContentHtml = "";
function setContentHtml(nextHtml) {
  if (lastContentHtml === nextHtml) return false;  // 字符串比较防抖
  content.innerHTML = nextHtml;
  lastContentHtml = nextHtml;
  R.bindDynamic();
  return true;
}
```

**优点**：有 `lastContentHtml` 字符串比较，避免相同内容重复 DOM 写入。

**隐患**：
- 字符串比较成本随视图复杂度上升
- 任意状态变更都触发 `render()` 重算所有视图函数
- 大视图（如 studio 图谱、clues 矩阵）全量 innerHTML 替换会丢滚动位置、输入焦点、动画态

### 3.3 play 端的局部 patch 模式

play 端有 `patchSyncChrome`、`patchGameView`、`patchGameSectionsTab` 等**局部 patch** 函数，能在不重渲的情况下更新局部 DOM。这是主应用应当借鉴的方向。

### 3.4 视图懒加载

主应用 `src/runtime/view-loader.js` 已实现视图模块按需加载（`ensureViewModules(view)`），`app.js` 的 `render()` 会在视图未就绪时先显示 loading 再异步加载。这一机制已经较好，可保留并强化。

### 3.5 API 层无缓存

`api/client.js` 没有任何客户端缓存。每次 `render()` 都可能触发新的 `GET` 请求。host 端的"粒度刷新"是缓解手段，但根因是缺缓存层。

### 3.6 资源加载

- Vite 6 + sourcemap 开启，构建产物已分块
- 官网 `zhimu-product-hero.png` 用 `preload`，但三端共享图重复引用
- 字体走 Google Fonts CDN（CSP 已放行）

## 四、安全现状

### 4.1 后端安全（扎实）

`backend/src/security-headers.js` + `app.js` 限流 + `auth.js` session：

| 项 | 状态 | 依据 |
|---|---|---|
| CSP（report-only / enforce） | ✅ | `security-headers.js`，生产默认 report-only，可 enforce |
| HSTS | ✅ | 生产环境 `max-age=31536000; includeSubDomains` |
| X-Content-Type-Options | ✅ | `nosniff` |
| X-Frame-Options | ✅ | `DENY`（frame-ancestors 'none'） |
| Referrer-Policy | ✅ | `strict-origin-when-cross-origin` |
| Permissions-Policy | ✅ | `camera=(), microphone=(self), geolocation=()` |
| 限流 | ✅ | 7 个 rate limiter（auth/guest/beta/write/read/upload/ai） |
| Session | ✅ | HttpOnly cookie + revocation |
| 上传扫描 | ✅ | strict + webhook/ClamAV 二选一 |
| OAuth | ✅ | 白名单 `accounts.google.com` / `github.com` |
| 生产可信七项 | ✅ | `check-production-ready.mjs` 阻断发布 |

### 4.2 前端安全（三端规范，主应用分散）

**play/、host/**：有独立的 `security.js`，集中了 `escapeHtml`、`isUuid`、`normalizeInviteCode`、`isSafeOAuthRedirectUrl`、`ALLOWED_OAUTH_PROVIDERS`、`sanitizeImageUrl`、`asArray`。

**主应用**：安全工具散落：
- `escapeHtml` 在 `src/utils/format.js`
- `isUuid` 未集中
- OAuth 校验在 `src/runtime/auth-session.js` 等处
- 无统一的 `security.js` 入口

### 4.3 innerHTML 审计

`scripts/audit-innerhtml.mjs` 已存在，应纳入 CI 强制门禁。当前 `src/` 下 102 处 innerHTML，需要逐处确认插值都经 `escapeHtml`。

### 4.4 已知风险

| 风险 | 现状 | 建议 |
|---|---|---|
| CSP 默认 report-only | 生产可 enforce 但默认未开 | 内测期切 enforce |
| 主应用 security 分散 | 无统一入口 | 抽 `src/security.js` |
| demo 模式下 `x-user-id` header | 仅本地 demoMode 走此分支 | 生产强制 `requireAuth`，已落地 |
| 三端 OAuth 校验重复 | 三份 `isSafeOAuthRedirectUrl` | 抽 shared-security |
| localStorage 存 `zhimuApiBase` | 可被注入篡改 API 端点 | 加 origin 白名单校验 |

## 五、产品与 UI 现状

### 5.1 产品定位（已立住）

官网 hero 文案：「让长线故事跑得起来、看得清楚、复盘有据。」
核心隐喻：「把'故事状态'变成团队共用的事实源。」

定位清晰，但**官网正文偏功能罗列**（"创作台 / 编排台 / 主持台 / 玩家端"四宫格），缺少场景化叙事和真实使用案例。

### 5.2 三端 UI 一致性

设计 token 统一（绿/黄铜/米色，Noto Serif SC + Inter），三端视觉连贯。但组件实现各自一套：
- `play/src/components/modal.js` vs `host/src/components/modal.js` vs `src/components/modal.js`
- `play/src/components/header.js` vs `host/src/components/header.js`
- 折叠面板、空状态、toast 等都有三份实现

### 5.3 交互反馈

- toast、loading 条、状态条齐全
- 部分场景缺骨架屏（如 host 进入监控台前、主应用切视图时）

### 5.4 响应式

- 官网：响应式良好

- host：桌面优先（监控台高密度）
- 主应用：桌面优先，移动端适配薄（侧边栏 248px 固定）
