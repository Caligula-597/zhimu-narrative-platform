## 一、现状：不是"代码丑"，是"工程失效"

### 1.1 模块边界形同虚设

看 `src/dom.js` 的真实代码：

```js
(function (window) {
  window.zhimuDom = {
    content: document.querySelector("#content"),
    toast: document.querySelector("#toast"),
    modalBackdrop: document.querySelector("#modal-backdrop"),
    modal: document.querySelector("#modal")
  };
  /** Deferred render — app.js registers zhimuRuntime.render after view modules load. */
  window.zhimuRender = function () {
    const fn = window.zhimuRuntime?.render;
    if (typeof fn === "function") fn();
  };
  window.zhimuGo = function (view) {
    const fn = window.zhimuRuntime?.go;
    if (typeof fn === "function") fn(view);
  };
})(window);
export {};
```

**问题**：
- `dom.js` 在 `app.js` 之前加载，但 `app.js` 才定义 `zhimuRuntime.render`。所以 `dom.js` 不得不写一个"延迟转发"的 `zhimuRender`，运行时去 `window.zhimuRuntime?.render` 查找。
- 这是**循环依赖的运行时绕过**。ES Modules 本可以用 `import { render } from "../app.js"` 让构建器解决，但 window 模式做不到。
- `dom.js` 顶部注释明说："Deferred render — app.js registers zhimuRuntime.render after view modules load."——作者自己也知道这是 hack。

- 删除 `formatBytes` 后，这里仍写着 `F.formatBytes || (() => "")`，**不会有任何警告**
- 改名一个函数要全文搜索 `window.zhimuFormat.xxx`，因为可能有 17 个视图都在用

  () => window.zhimuActionsPlayer?.handlePlayerAction,

  for (const getFn of dispatchers) {
    const fn = getFn();
    if (typeof fn === "function" && fn(action, el)) return;

**问题**：
- 11 个 dispatcher 顺序遍历，谁先返回 true 谁处理

- 新增一个领域要改这个数组（中心化注册）
- 每次点击都遍历 11 个 `() => window.zhimuActionsXxx?.handleXxxAction`，微优化空间都没有

### 2.2 状态层：分片 store + 轻量订阅

`src/state/create-store.js`（新增）：

```js
// src/state/create-store.js
export function createStore(initial) {
  let state = { ...initial };
  const listeners = new Set();
  return {
    get: () => state,
    set(patch) {
      const prev = state;
      state = { ...state, ...patch };
      if (listeners.size) listeners.forEach((fn) => fn(state, prev));
    },
    subscribe(fn) {
      listeners.add(fn);
      return () => listeners.delete(fn);
    }
  };
}
```

### 2.5 dispatcher：从责任链到显式注册

`src/runtime/actions.js` 迁移后：

```js
// src/runtime/actions.js
import { state } from "../state/index.js";
import { showToast } from "../components/toast.js";
import { openModal } from "../components/modal.js";

// 显式注册表，不再遍历 11 个 window 查找
const handlers = new Map();
export function registerAction(prefix, handler) {
  handlers.set(prefix, handler);
}

export function handle(action, el) {
  // action 命名约定：domain:verb，如 "studio:save-node"
  const [prefix] = action.split(":");
  const handler = handlers.get(prefix);
  if (handler) return handler(action, el);
  // fallback
  if (action === "save-node") return showToast("配置已保存");
  // ...
}
```

各 actions 模块自己注册：

// src/runtime/actions-studio.js
import { registerAction } from "./actions.js";

registerAction("studio", (action, el) => {
  // studio 相关 action 处理
});

- O(1) 查找替代 O(11) 遍历
- 命名冲突在注册期发现（`handlers.set` 重复 key 警告）
- 新增领域只在自己模块注册，不动中心数组

## 三、桥接策略：迁移中业务不中断

这是整个迁移最关键的部分。**核心原则：迁移期两种模式并存，旧代码靠 `window.*` 继续工作，新代码用 `import`**。

### 3.1 双导出模式

每个迁移完成的模块同时做两件事：

```js
// src/utils/format.js（迁移后）
export function formatTime(value) { ... }
export function escapeHtml(value = "") { ... }
// ...

// 桥接：让旧代码继续工作
if (typeof window !== "undefined") {
  window.zhimuFormat = {
    formatTime, escapeHtml, formatBytes, formatRelativeTime, roleParts,
    // ... 全部导出
  };
}
```

- 旧视图 `const F = window.zhimuFormat || {}` 继续工作
- 新视图 `import { escapeHtml } from "../utils/format.js"` 直接用
- 全部视图迁完后，删除 `window.zhimuFormat = ...` 桥接段

### 3.3 每个迁移单元的验收清单

每个文件迁完都跑：

```powershell

# 3. 关键路径 E2E（chromium 足够）

```

任何一步红立即停，revert 这个 commit，不继续下一步。

### 3.4 桥接删除时机

**不要边迁边删桥接**。等全部迁移完成（第 5 层 app.js 迁完）后，统一做一次"桥接清理"PR：

- 删除所有 `window.zhimuXxx = ...` 赋值
- 删除 `src/runtime/dependency-guard.js`（不再需要）
- 删除 `frontend/main.js` 的 import 列表
- 删除各视图的 `const F = window.zhimuFormat || {}` 别名

这次清理是**纯删除**，不改业务逻辑，最容易 review。

## 四、预期效果：能解锁什么现在做不到的事

### 4.1 工程效率突破

| 现在 | 迁移后 |
|---|---|
| 改名一个函数要全文搜索 `window.zhimuFormat.xxx`，可能漏 | IDE 全局重命名，编译期保证一致 |
| 删除一个函数后，引用处仍写 `F.formatBytes \|\| (() => "")`，无警告 | 删除后 import 处编译报错 |
| 跳转定义失效，`F` 是 `window.zhimuFormat \|\| {}` | Cmd+Click 直接跳到 `format.js` |
| 新人看视图文件要先看懂 30 行别名拉取 | import 列表清晰，3 秒看懂依赖 |
| Tree-shaking 失效，599 行 api 全进 bundle | 只 import 的领域进 bundle，首屏体积下降 |

### 4.2 性能突破

**首屏 bundle 体积下降**（量化预估）：
- 现在 `api/client.js` 599 行整体打包，哪怕首屏只用到 `auth.me` + `world.list`
- 迁移后按领域 import，Vite 自动代码分割，首屏只加载 `auth.js` + `world.js`
- 预估首屏 JS 体积下降 30-40%（需 build 后实测）

**视图懒加载真正生效**：
- 现在 `frontend/main.js` 顶部 import 所有视图，所有视图代码进首屏
- 迁移后 `view-loader.js` 用动态 `import("../views/xxx.js")`，视图首次访问才加载
- 预估首屏加载时间下降 20-30%

**细粒度订阅解锁局部更新**：
- 现在 `state.studioZoom = 1.2` 必须手动 `render()` 全量重渲
- 迁移后 `subscribeStudio((next, prev) => { if (next.studioZoom !== prev.studioZoom) patchZoom(); })`，只更新缩放控件
- studio 图谱拖拽、clues 搜索过滤不再丢滚动位置和输入焦点

### 4.3 架构突破

**循环依赖消除**：
- 现在 `dom.js` ↔ `app.js` 靠 `window.zhimuRuntime?.render` 运行时绕过
- 迁移后 ES Modules 静态分析，构建期解决，无运行时查找开销

**dispatcher 可扩展性**：
- 现在 11 个领域挤在一个数组，新增领域要改中心文件
- 迁移后各领域自注册，完全解耦，新增领域零冲突

**状态变更可追踪**：
- 现在 `state.studioZoom = 1.2` 无任何通知，调试要打 console.log
- 迁移后 store 自带 subscribe，可加 dev 模式 logger 自动记录所有 set

**测试可写性**：
- 现在 `overview()` 视图函数依赖 `window.zhimuState`、`window.zhimuApi`，无法单测
- 迁移后 `overview(state, api)` 纯函数化（或 import 注入），可写快照测试

### 4.4 三端共享解锁

主应用迁移完成后，`shared/` 共享层可被四端统一引用：
- `shared/security.js`：四端共用 escapeHtml/isUuid/OAuth 校验
- `shared/api-fetch.js`：四端共用 fetch 封装
- `shared/components/`：四端共用 modal/toast/collapse-panel

修一个 bug 改一处，四端生效。这是当前完全做不到的。

### 4.5 后续功能解锁

迁移完成后，这些现在做不动的能力变可行：

| 能力 | 现在为什么做不动 | 迁移后 |
|---|---|---|
| 协同编辑实时冲突 UI | 状态平铺，无法追踪谁在改什么 | 分片 store + subscribe，可推送 revision 变更 |
| 知识块检索产品化 | API client 单体，加新领域要改 599 行 | 加 `src/api/knowledge.js` 即可 |
| 创作者 overview 聚合 API 接入 | 视图靠 30 个 window 拉取，聚合数据难注入 | 视图 import 显式，聚合 API 直接传 |
| 主应用移动端适配 | 全量 innerHTML 重渲，移动端性能差 | 局部 patch + 细粒度订阅，移动端可用 |
| TypeScript 渐进引入 | window.* 无类型 | ES Modules 可加 JSDoc 或 .d.ts |

## 五、风险与边界

### 5.1 迁移期风险

| 风险 | 概率 | 应对 |
|---|---|---|
| 桥接段遗漏，旧代码运行时 `window.zhimuXxx` undefined | 中 | `dependency-guard.js` 迁移期保留并强化，缺全局直接报错 |
| Proxy 兼容桥性能损耗 | 低 | Proxy 仅迁移期用，迁完删除；实测 < 0.1ms/次读写 |
| 视图迁移顺序错导致循环 import | 中 | Vite 构建期报错，立即停 |
| 新旧代码混用导致行为不一致 | 中 | 桥接段严格 1:1 映射，不改语义 |

### 5.2 不在本次迁移范围内的事

- ❌ 不改业务逻辑（视图函数体不动，只改 import 方式）
- ❌ 不改 API 契约（请求路径/方法/响应不变）
- ❌ 不改 DOM 结构（HTML 模板字符串不变）
- ❌ 不改 CSS（样式完全不动）
- ❌ 不引入 TypeScript（仅迁移模块化，类型化是后续 P2）
- ❌ 不引入框架（仍是原生 ES Modules + 命令式 render）
- ❌ 不改后端（后端架构健康，不动）

### 5.3 迁移完成的判断标准

```powershell
# 1. 全部测试通过
cd backend && npm test && cd ..
npm run check:modules
npm run build
npm run test:e2e
npm run audit:innerhtml

# 2. 桥接段全部删除后仍工作
grep -r "window.zhimu" src/   # 应返回 0 结果（除 config.js）

# 3. dependency-guard.js 可删除
# 4. frontend/main.js 缩短为单行 import
# 5. 首屏 JS 体积下降 > 20%（实测）
```

## 六、与 play/host 现状的对比

play/host 已经是迁移后的形态，可作为参照：

| 维度 | 主应用现状 | play/host 现状 | 主应用迁移后 |
|---|---|---|---|
| 模块化 | window.* + IIFE | 真 ES Modules | 真 ES Modules |
| 视图依赖 | 30 行别名拉取 | 顶部 import | 顶部 import |
| API 客户端 | 599 行单体 | `play/src/api.js` 按需 | 按领域拆分 |
| 状态 | 60+ 属性平铺 | `play/src/state.js` 模块导出 | 分片 store |
| dispatcher | 11 个 window 遍历 | 无（play 用事件直接绑） | 注册表 |
| 循环依赖 | 运行时 `?.` 绕过 | 静态 import 解决 | 静态 import 解决 |
| Tree-shaking | 失效 | 生效 | 生效 |
| 三端共享 | 不可能 | 部分（各自 api.js） | 通过 shared/ 共享 |

**结论**：迁移完成后，主应用架构水平对齐 play/host，并在此基础上多出"分片 store + API 领域拆分 + shared/ 共享"三项 play/host 也未完全做到的能力。

## 七、一句话总结

主应用模块化迁移不是"代码美化"，是**把一个 IDE 跳不转、Tree-shake 不掉、循环依赖靠运行时绕过、状态变更无订阅、新功能加不动**的代码库，改造成**和 play/host 同等水平、且能支撑后续协同编辑/知识块/移动端/TypeScript 的可演进架构**。

迁移方式是**渐进式 + 双导出桥接 + 每步 e2e 验证**，业务代码在迁移期完全无感，迁移完成后才统一清理桥接。

最大风险是迁移期工作量大（预估 2-4 周），但每一步都有独立回滚路径，不会出现"迁一半动不了"的死锁。
