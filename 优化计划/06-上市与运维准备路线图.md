## 一、目标

织幕接下来不再按“小范围能跑”的标准推进，而要按可上市、可运维、可交付客户的产品标准治理。

上市准备的核心不是继续堆功能，而是让产品具备以下能力：

| 维度 | 上市要求 |
|---|---|
| 稳定性 | 核心流程可重复跑通，部署可回滚，异常可定位 |
| 数据安全 | 用户数据、剧本内容、附件、运行记录不误删、不串权、不泄露 |
| 权限可信 | 创作者、协作者、主持人、玩家、运营的访问边界清楚 |
| 运维可见 | 健康检查、日志、告警、监控、审计链路真实可用 |
| 产品闭环 | 新用户能完成注册、创作、开房、邀请、游玩、复盘 |
| 商业可承接 | 有内测支持、人工扩容、价格草案、客户反馈与升级路径 |

---

## 二、当前判断

织幕已经具备上市前的主体基础：

- 后端领域拆分、权限、审计、迁移、生产门槛、上传扫描、告警底座较扎实。
- 主应用、玩家端、主持端、官网四端已经形成产品闭环。
- 线索、规则、运行房、存档、复盘、附件、公开剧本库等核心业务已经不是 demo 级别。
- 目前最大短板不是后端能力，而是主应用前端状态和共享层仍在收尾期。

当前阶段应定义为：

```text
可信 Beta 后期：可内测、可试点，但还不应大规模公开商业化。
```

## 三、阶段规划

### 阶段 1：内测可运维版

建议周期：2-4 周

目标：少量真实团队可以稳定试用，出现问题时团队能定位、恢复和人工兜底。

必须完成：

| 编号 | 事项 | 说明 | 验收 |
|---|---|---|---|
| L1-01 | A1/A2 前端状态收口 | A2 `zhimuState` 消费者迁移已完成；三大桥（zhimuViews/zhimuRuntime/zhimuDom）已全部清除 | `check:modules`、`build`、`test:runtime-stores` 通过，剩余桥接有清单 |
| L1-01a | CI 门禁整理 | `play/` 依赖安装已提前到 `test:play` 前；CodeQL 因仓库未启用 code scanning 暂设为非阻塞；API smoke 复盘断言已同步后端 `postgame` 语义；UI smoke 已同步 view registry 懒加载结构；主线 Playwright E2E 收敛为 Chromium 门禁、加 20 分钟步骤超时、首个失败即停并上传 report/trace | GitHub Actions 不再因缺 `livekit-client`、SARIF 上传配置错误、旧复盘断言、旧 view-resolver 断言或无限等待 E2E 阻断主线；E2E 失败可追溯到截图和 trace |
| L1-02 | 关键流程 E2E | 创作、开房、玩家加入、主持推进、线索发放、复盘；已修复创作者向导邀请码断言的 strict mode 冲突，将主持端 E2E 入口迁移到独立 `host/` 控制台，并补齐 host webServer / fixture 去重 / host helper 去状态桥读取 | Chromium 至少全绿；失败项有记录 |
| L1-03 | 生产门槛真实可过 | CSP、OTLP、告警、上传扫描、OPS token、metrics token | `npm run check:production-ready` 通过 |
| L1-04 | 数据备份与恢复演练 | Postgres 备份、恢复到新库、R2 策略确认 | 形成一次演练记录 |
| L1-05 | 权限矩阵复查 | world、room、role、catalog、ops、asset 权限边界 | 后端权限测试通过，人工抽查关键 API |
| L1-06 | 内测支持闭环 | 申请、审批、人工扩容、问题反馈、邮件模板 | support SOP 可执行 |
| L1-07 | Staging 与生产隔离 | 数据库、R2 bucket、环境变量、域名明确分离 | staging smoke 通过 |

阶段 1 可接受风险：

- 部分 UI 还不够精致。
- 商业支付可以暂不公开。
- 少量后台操作仍由 OPS 手动处理。
- 前端桥接可以保留，但必须有清单和退场计划。

阶段 1 不可接受风险：

- 剧本、线索、角色、玩家数据串世界或串房间。
- 上传文件未经过生产可信扫描策略。
- 生产无告警、无日志、无健康检查。
- 无法恢复数据库或不知道如何恢复。
- 权限错误导致玩家看到不该看的内容。

### 阶段 2：公开 Beta

建议周期：4-8 周

目标：陌生用户可以从官网进入产品，不需要团队手把手陪跑，也能完成第一次体验。

必须完成：

| 编号 | 事项 | 说明 | 验收 |
|---|---|---|---|
| L2-01 | 创作者制作总控台 | 世界总览升级为制作状态、风险、下一步建议 | 新用户能看懂下一步该做什么 |
| L2-02 | 主持端运行控制台 | 首页聚合玩家、待确认、线索、日志、风险 | 主持人开场前 30 秒内掌握房间状态 |
| L2-03 | 玩家下一步行动 | 玩家端首页明确“读什么、查什么、等什么” | 玩家不依赖主持口头解释即可继续 |
| L2-04 | Clue audit 报告 | 线索管理只做审稿与证据链检查，不扩成完整编排台 | 能发现孤立线索、缺条件、缺归属 |
| L2-05 | Rule debug trace | 自动化规则可解释：为什么触发、为什么没触发 | 支持主持/创作者自查 |
| L2-06 | 真实官网资产 | 官网使用真实截图、清晰定位、案例或匿名 pilot | 官网不再依赖愿景图 |
| L2-07 | 反馈与故障入口 | 产品内有反馈、报错、联系支持入口 | 用户能提交问题并被追踪 |
| L2-08 | 监控告警值班规则 | 谁收到告警、多久响应、如何升级 | 形成运维值班说明 |

阶段 2 可接受风险：

- 支付仍可人工开通。
- 高级协同编辑可标注为测试功能。
- 小游戏框架可作为“创作者测试功能”开放，不承诺稳定 SLA。

阶段 2 不可接受风险：

- 新用户无法完成首次体验。
- 公开 Beta 用户遇到错误没有反馈路径。
- 关键错误只有浏览器控制台可见，后端或运维无记录。

### 阶段 3：商业化准备

建议周期：8-12 周

目标：可以承接工作室、社群、长线内容团队试点付费或企业试用。

必须完成：

| 编号 | 事项 | 说明 | 验收 |
|---|---|---|---|
| L3-01 | 套餐与配额策略 | free、beta、creator、studio 等权益清晰 | 配额 UI、OPS 开通、文档一致 |
| L3-02 | 支付或人工开通 SOP | Stripe 未公开前保留人工开通流程 | 支持订单、发票、开通记录 |
| L3-03 | 客户交付包 | 内容导入、导出、迁移、备份说明 | 可交付给试点客户 |
| L3-04 | SLA 草案 | 响应时间、数据恢复、维护窗口 | 对外可解释，对内可执行 |
| L3-05 | 客户成功手册 | 首次导入、首场运行、复盘、扩容 | 支持人员可按文档操作 |
| L3-06 | 运维 Runbook 演练 | DB、R2、告警、邮件、OAuth、上传扫描故障 | 至少季度演练 |
| L3-07 | 合规文档补齐 | 隐私、用户协议、数据删除、内容审核 | 官网与产品入口可访问 |

阶段 3 可接受风险：

- 暂不支持大企业私有化。
- 暂不承诺 24/7 企业 SLA。
- 高级 BI、复杂团队权限可后置。

阶段 3 不可接受风险：

- 收费用户无人工支持和升级记录。
- 账单、配额、权限之间不一致。
- 无法解释用户数据保存、删除、导出策略。

## 四、上市门槛清单

以下清单是从“可以上线给陌生用户”角度定义的最低门槛。

### 1. 产品门槛

- [ ] 官网清楚说明织幕是什么、不是什么。
- [ ] 官网使用真实三端截图，而不是愿景占位图。
- [ ] 新用户能完成注册或申请内测。
- [ ] 创作者能创建世界、配置角色、创建测试房。
- [ ] 玩家能通过邀请码进入、选角、阅读、获得线索。
- [ ] 主持人能看到玩家进度、待确认事件、运行日志。
- [ ] 用户遇到问题能找到反馈入口。

### 2. 工程门槛

- [ ] `npm run check:modules` 通过。
- [ ] `npm run build` 通过。
- [ ] `npm run test:runtime-stores` 通过。
- [ ] 后端 `check`、`check:schemas`、`check:boot`、`test` 通过。
- [ ] E2E 覆盖创作、开房、玩家加入、主持推进。
- [ ] 迁移脚本、历史脚本不会误覆盖现代模块。
- [ ] 所有测试功能明确标注，不与稳定功能混淆。

### 3. 安全门槛

- [ ] 生产强制正式 session/auth，不依赖 demo header。
- [ ] CSP enforce 或明确 report-only 清零计划。
- [ ] `audit:innerhtml` 进入 CI。
- [ ] 上传扫描生产策略为 strict。
- [x] Supabase/public schema 业务表启用 RLS，无匿名直连读写面。已补 `045_enable_public_rls.sql`，并用 `security-migrations.test.js` 防止新表漏配。
- [ ] 公开剧本库必须人工审核。
- [ ] 玩家端社区或公开大厅具备基础内容安全策略。
- [ ] OPS、metrics、admin 类接口有独立 token 或权限保护。

### 4. 数据门槛

- [ ] Postgres 自动备份策略明确。
- [ ] 至少完成一次恢复演练。
- [ ] R2/S3 bucket 与生产、staging 分离。
- [ ] 附件删除、回收站、永久删除策略清楚。
- [ ] 用户数据删除与导出策略有文档。
- [ ] 内容包导出可作为客户备份手段。

### 5. 运维门槛

- [ ] `/api/health` 和 `/api/health/ready` 可用。
- [ ] `monitoring:smoke` 可运行。
- [ ] 告警 webhook 真实可达。
- [ ] OTLP 或等价 tracing/logging 可用。
- [ ] 部署失败能回滚。
- [ ] 生产环境变量有清单和负责人。
- [ ] staging 可复现生产主要流程。

## 九、管理规则

1. 上市前的每个功能都必须标注稳定等级：
   - 稳定功能：可对外承诺。
   - Beta 功能：可给内测用户使用，有人工支持。
   - 测试功能：只用于探索，不承诺数据或交互稳定。

2. 每个架构迁移必须满足：
   - 小批次。
   - 可回滚。
   - 不改变业务行为。
   - 有验证命令。
   - 有剩余风险说明。

3. 每个后端新增接口必须满足：
   - 权限明确。
   - schema 明确。
   - 错误码可解释。
   - 至少一条测试或 smoke 覆盖。

4. 每个公开入口必须满足：
   - 用户知道自己在哪里。
   - 用户知道下一步做什么。
   - 用户知道出问题找谁。
   - 运营知道后台如何处理。

## 十、最终上市判断

织幕可以进入公开上市/商业试点的判断标准：

```text
一个完全陌生的创作者，从官网进入织幕，
能完成注册或申请、创建世界、配置角色、创建测试房、
邀请玩家进入、主持推进一次关键事件、完成一次复盘，
过程中不需要开发人员介入。

如果中途发生错误，
用户能看到可理解的提示，
运营能收到或查询到记录，
工程能从日志、监控、审计中定位问题，
数据能通过备份或存档机制恢复。
```

达到这个标准后，织幕才不是“能演示”，而是“能运营”。
