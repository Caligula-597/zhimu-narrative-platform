## 一、产品定位：从"功能罗列"到"一句话锋利"

### 1.1 现状

官网 hero：「让长线故事跑得起来、看得清楚、复盘有据。」
报名帖：「线上长线互动叙事引擎」
核心隐喻：「把'故事状态'变成团队共用的事实源」

定位本身没问题，但**信息密度不够、记忆点不锋利**。用户读完 hero 不知道织幕和"飞书文档 + 微信群 + 骰子 Bot"的区别。

### 1.2 锋利化建议

**一句话定位（建议）**：

> 织幕是长线剧本杀的「故事状态机」——把谁知道什么、何时知道、为什么知道，从群聊和表格里收束进系统。

**三个记忆点**：

1. **状态机**：不是文档编辑器，是可运行的故事系统。每一条线索、每一次解锁、每一场主持干预都是状态变更，可追溯、可回滚。
2. **三端分权**：创作者做结构、主持人做调度、玩家做体验，同一份故事状态，三种视角。不再是"一个 DM 在群里手动对账"。
3. **长线可持续**：平行房、checkpoint、recap，让故事能跑数周数月而不失控。这是织幕与"一局制线上剧本杀工具"的本质差异。

### 1.3 反面定位（明确"织幕不是什么"）

| 织幕不是 | 区别 |
|---|---|
| 不是飞书/Notion | 它们是文档，织幕是状态机；文档是死快照，织幕是活的运行时 |
| 不是骰子 Bot / 跑团 VTT | 它们解决"掷骰子 + 战术地图"，织幕解决"长线剧情的状态追踪与复盘" |
| 不是一局制剧本杀平台 | 一局制是 2-4 小时单场，织幕面向 1-12 周的长线叙事 |
| 不是 AI 故事生成器 | AI 是创作助手，不是替代作者；织幕尊重作者主权 |

建议在官网"产品定位"段加一个**「织幕不是什么」对照表**，比正面陈述更易记忆。

## 二、官网文案优化

### 2.1 现状评估

`site/index.html` 结构完整：hero / product / showcase / workflow / status / systems / role / import / pricing / beta。

**问题**：
- hero 文案偏抽象，缺"使用前后对比"
- showcase 四宫格用的是同一张 `zhimu-product-hero.png`，没体现三端差异
- workflow 四步是"建立世界 / 编排推进 / 开房运行 / 存档复盘"，太功能化
- status 段落较长，缺数据可视化
- 缺真实案例 / pilot 团队故事

### 2.2 hero 段优化

**当前**：
> 让长线故事跑得起来、看得清楚、复盘有据。
> 织幕面向剧本杀工作室、长线本作者、线上主持人，把剧本结构、角色分屏、线索流转、规则触发、玩家进度和主持干预沉淀为同一套可追踪的运行状态。

**建议改为**（场景化 + 对比）：

> **长线剧本杀，不该靠群聊手动对账。**
>
> 织幕把"谁知道什么、何时知道、为什么知道"收束进同一套可运行的故事状态机。
> 创作者做结构，主持人做调度，玩家做体验——
> 故事能跑数周数月不失控，复盘有据，改本有谱。

hero 下方加一个**「使用前后」对比卡**：

| 没有织幕 | 用织幕 |
|---|---|
| DM 在微信群手动记线索发放 | 系统按规则自动发放，留痕可审计 |
| 玩家进度靠翻聊天记录 | 每个角色有独立分屏，进度一目了然 |
| 长线本开到第三周就乱 | checkpoint + recap 让故事可持续 |
| 复盘靠群主口述 | 时间线 + 线索流转图 + 存档快照 |
| 改本靠记忆"上次改到哪" | 内容版本 + 协同编辑 + 影响范围检查 |

### 2.3 showcase 段优化

**当前**：四张图，三张是 `zhimu-product-hero.png`，一张是 `site-preview.svg`。

**建议**：
- 为三端各做一张**真实截图**（不是同一张 hero 图）
- 创作者端：展示 studio 图谱 + 线索矩阵的真实界面
- 主持端：展示监控台待确认事件 + 玩家进度的真实界面
- 玩家端：展示分屏阅读 + 线索册的真实界面
- 复盘：展示 recap 时间线 + 线索流转图

截图可用 staging 环境真实截取，比设计稿更可信。

### 2.4 workflow 段优化

**当前**：建立世界 / 编排推进 / 开房运行 / 存档复盘

**建议**：每步加一句"痛点 → 解法"对照：

1. **建立世界**——把散在 Word/飞书的设定，收进结构化的世界、角色、章节、线索。
2. **编排推进**——场景、调查点、规则自动化，让故事能"自己往前走"。
3. **开房运行**——平行房 + 邀请码入房，主持只管关键节点，不再当人工数据库。
4. **存档复盘**——checkpoint + recap + 线索流转，每一场故事都能留下来。

### 2.5 status 段优化

**当前**：可信 Beta 末期的文字描述。

**建议**：加一个**可视化进度条**：
- 核心闭环：100%（创作/开房/探索/规则/主持/复盘）
- 安全门禁：100%（CSP/AV/限流/session/OTEL）
- 三端独立：90%（play/host/site 已上线，主应用待模块化）
- 商业化：30%（定价草案 + Stripe 底座，未公开支付）
- 内测团队：N 个（pilot tracker 实时数据）

### 2.6 新增"案例"段（P1）

内测期补 2-3 个 pilot 团队故事：

- **案例模板**：团队名（匿名） / 规模 / 用织幕前痛点 / 用织幕后变化 / 一句话推荐
- **示例**：「某线上剧本杀工作室，8 人长线本，过去开到第三周玩家就流失；用织幕后跑到第 8 周完结，复盘时主持人说'第一次不用脑子记谁有什么线索'」

案例比任何功能介绍都有说服力。可放 `docs/ops/PILOT_TRACKER.md` 的脱敏数据。

- `创意提案-织幕/创意提案-织幕.html`：已存在，是参赛/报名用的完整方案
- `创意提案-织幕/报名帖文案.txt`：已存在，定位清晰

**问题**：两份物料的**视觉风格、文案口径、功能描述未完全对齐**。创意提案是早期版本，官网是迭代后版本，存在信息差。

### 3.2 对齐建议

4. **报名帖文案**：与官网 hero 一句话定位一致，加一句"评委可访问 staging 体验"链接

### 3.3 创意提案补强

创意提案当前偏"产品介绍"，建议补：
- **技术亮点**（评委关心）：Fastify 5 + PostgreSQL 真相源、CSP + AV strict 安全门禁、DeepSeek 多阶段创作 pipeline、OpenTelemetry 可观测、44 个 SQL migrations 的演进能力
- **数据**（评委关心）：44 migrations、40+ 路由模块、4 端、7 项生产可信门禁、3 浏览器 E2E 矩阵
- **可持续性**（评委关心）：SaaS 订阅 + 剧本市集 + 增值服务的三层商业模式

## 四、Beta onboarding 优化

### 4.1 现状

官网 `#beta` 段有表单：称呼 / 邮箱 / 使用意向 / 预计规模 / 想优先解决什么 / 其他联系方式。表单提交到 `/api/platform/beta/apply`。

**问题**：
- 表单是"被动收集"，用户提交后无即时反馈
- 没有"提交后下一步是什么"的引导
- 内测申请和直接注册两个入口并存，用户不知道选哪个

### 4.2 引导式 onboarding 建议

**流程**：

1. 用户访问官网 → hero 有"创作者注册"和"提交内测申请"两入口
2. 选"创作者注册" → 直接进主应用注册 → 注册后引导创建第一个世界（wizard 已有）
3. 选"提交内测申请" → 表单提交后**立即显示**：
   - "收到，1-2 个工作日内联系你"
   - "想先体验？可以[直接注册]试用免费版"
   - "加运营微信 / 邮件 support@getzhimu.com 加急"
4. 邮件确认 → `docs/ops/BETA_ONBOARDING_CHECKLIST_ZH.md` 的 SOP 执行
5. 首次登录主应用 → onboarding-strip（已有）+ first-run-chooser（已有）引导

**关键**：让"内测申请"和"直接注册"两个入口**互通**，而不是二选一。提交申请的用户也能立即试用，试用后转正时配额人工扩容。

### 4.3 首次体验优化

主应用 `src/components/onboarding-strip.js` + `first-run-chooser.js` 已有底座。强化：
- 首次进入显示"3 步快速上手"：建世界 → 编一幕 → 开测试房
- 每步完成打勾，可跳过
- 提供"从模板开始"和"从导入开始"两条路径
- 导入路径显示 `docs/ops/IMPORT_SCRIPT_SOP_ZH.md` 的简化版

## 五、定价策略优化

### 5.1 现状

- 官网 `#pricing` 段：免费版 / 创作者 / 工作室三档（2/10/50 剧本，500MB/2GB/10GB 存储）
- `site/pricing-commercial.html`：内部预览，未公开
- `docs/PRICING_DRAFT_ZH.md`：定价草案
- 当前无在线支付，靠"登录后申请升级"+ 邮件人工处理
- 后端 Stripe billing 底座已具备

### 5.2 建议

**内测期（当前）**：
- 维持"免费试用 + 人工扩容"，但在官网明确标注"内测期免费"
- 三档定价改为"配额指引"而非"价格"，避免用户找支付入口找不到
- 邮件申请升级流程加 SLA 承诺（1-2 工作日）

**公测期（Stripe 启用后）**：
- 公开 `pricing-commercial.html`，明确月费/年费
- 免费版保留（体验用），创作者档 ¥XX/月，工作室档 ¥XXX/月
- 加"剧本市集抽成"说明（创作者卖剧本，平台抽 X%）
- 年付优惠

**成熟期**：
- 增值服务：AI 创作额度包、语音时长包、高级数据分析
- 企业定制：私有部署、SSO、定制开发

### 5.3 定价页文案

当前 `pricing-commercial.html` 是内部预览。公开前建议：
- 加"为什么这样定价"段落（按使用量而非按席位，对创作者友好）
- 加"与同类工具对比"（飞书/Notion 按席位，织幕按世界数 + 存储）
- 加 FAQ（能不能换套餐、能不能退款、数据归属）

## 八、一句话总结

织幕的产品力已经够用，**当前宣传的核心问题是"讲得太抽象、缺真实案例"**。

P1 优先做三件事：
1. **官网 hero 锋利化** + 加"使用前后对比" + 加"不是什么对照"
2. **showcase 换真实截图** + 新增 pilot 案例段
3. **创意提案与官网对齐** + 补技术亮点与数据

这三件事不需要改代码架构，只需文案 + 截图 + 案例整理，是性价比最高的宣传提升。
