# 织幕创作者机制设计与多审查工作台 V1

## 1. 产品目标

织幕不应承诺“AI 自动写出没有逻辑问题的完整剧本”。更可信的产品承诺是：

> 作者负责创作判断，AI 负责提供候选方案和对抗性意见，确定性程序负责验证结构能否运行，平台负责保存版本、问题证据与作者决策。

工作台解决三件事：

1. 新人不需要理解 JSON，也能把一个模糊点子整理成可运行的机制。
2. 作者不必把每一篇作品单独交给外部人员复核，平台可以完成日常结构检查和独立 AI 压力测试。
3. 平台不假装替代资深编辑；审美、动机强度、情感价值和最终取舍仍由人决定。

## 2. 三类能力必须分开

### 2.1 创作辅助

负责给作者灵感、提供机制卡、补充备选方案。它可以生成，但没有通过或驳回作品的权力。

### 2.2 确定性验证

由普通程序完成，不调用语言模型。负责状态、资源、引用、路径与数据类型等可以精确验证的问题。

### 2.3 独立审查

由与生成会话隔离的审查器完成。审查器只找问题、引用依据、给出复现方式，不直接重写作品。

生成、验证和审查不得合并为同一个提示词中的“先写再自检”。

## 3. 作者实际使用流程

```mermaid
flowchart LR
  A["创意立项"] --> B["机制设计七问"]
  B --> C["选择或改造机制卡"]
  C --> D["组装可玩循环"]
  D --> E["章节因果映射"]
  E --> F["确定性模拟"]
  F --> G["独立 AI 审查"]
  G --> H["作者处理或说明豁免"]
  H --> I["冻结版本并进入扩写"]
```

作者可以随时保存草稿。只有“进入扩写”“提交测试”“准备发布”三个检查点需要运行完整复核。

## 4. 新人机制设计向导

界面一次只问一个问题，提供例子、反例和“从机制卡填入”按钮。作者看到的是自然语言，不显示 `stateKey`、枚举值或资源内部编号。

### 第一问：玩家反复执行的具体动作是什么？

合格示例：

- 提出一次程序异议，并说明它针对哪份证据。
- 把有限氧气分配给一处舱室。
- 选择公开一段记忆，换取一名角色的访问权。
- 向一个玩具提出只能回答“是、否、沉默”的问题。

不合格示例：调查真相、推动剧情、进行讨论、作出选择。

### 第二问：玩家为什么不能全部合作？

至少明确一种可执行冲突：

- 有限资源；
- 互斥权限；
- 目标不一致；
- 信息不对称；
- 公开秘密会伤害自己；
- 一人获益会使另一人失去资格。

### 第三问：有限资源是什么？

资源必须属于故事世界，并写明初始数量、持有者、获取方式、消耗方式和下限。

不建议使用“决策点”“行动容量”“通用信任值”。如果一个资源换掉名字后能出现在任何题材里，系统应提示作者继续题材化。

### 第四问：选择之后立刻发生什么？

反馈应是玩家能观察到的世界变化，例如门被打开、证据被封存、某人失去权限、观众叙事改变、植物释放记忆或角色身份被公开。

“影响后续剧情”“关系发生变化”不算完整反馈。

### 第五问：失败后怎样继续？

失败必须改变局面，而不是让流程停止：

- 获得不完整信息；
- 额外消耗资源；
- 暴露行动者；
- 关闭一条路线并打开另一条高风险路线；
- 延迟进入，但 NPC 或环境状态恶化。

### 第六问：为什么这个机制属于当前题材？

作者需要指出机制依赖的职业流程、世界规则、空间、技术或社会关系。系统可以做“名词替换测试”：把题材名词换成通用名词后仍完全成立的机制，需要作者进一步改造。

### 第七问：早期选择怎样抵达结局？

作者至少连接两条完整因果链：

> 第几章的世界内行为 → 写入什么变化 → 后续哪一章读取 → 改变什么机会或代价 → 哪条结局读取。

仅在最后一章投票不算累计结局。

## 5. 可玩循环装配器

完成七问后，平台把答案整理成作者可读的循环，而不是要求作者填写完整状态机：

| 部分 | 作者看到的内容 | 系统保存的结构 |
|---|---|---|
| 输入 | 玩家此时知道什么、拥有什么 | stateReads、resourceReads |
| 动作 | 玩家在世界中具体做什么 | choiceText、actionTarget |
| 反馈 | 玩家立刻看到什么变化 | visibleFeedback |
| 代价 | 谁失去什么、什么不可恢复 | resourceDelta、locks |
| 后果 | 后续哪章发生变化 | stateWrites、unlocks |
| 失败前进 | 未满足条件时如何继续 | onFail、fallbackCost |

系统内部字段只在“高级模式”和审查报告中显示，默认创作界面不暴露状态机语言。

## 6. 机制卡片库

### 6.1 卡片字段

```json
{
  "id": "evidence-objection",
  "name": "证据资格异议",
  "applicableGenres": ["法庭", "调查", "政治程序"],
  "repeatedAction": "针对一份材料提出具体程序异议",
  "limitedResource": "正式异议次数或法定陈述时间",
  "informationStructure": "不同角色掌握来源、程序和内容中的不同部分",
  "successFeedback": "材料暂缓采纳，并开放来源复核",
  "failureFeedback": "材料继续生效，但异议者获得一项可用于上诉的程序记录",
  "commonPitfalls": ["把异议写成普通投票", "成功才推进、失败无事发生"],
  "variants": ["听证会", "董事会合规审查", "联盟赛事仲裁"],
  "completeExample": "第二章针对医疗记录提出来源异议，消耗一次陈述时间，换取冷柜原始登记。",
  "unsuitableWhen": "作品没有明确程序规则，主持人也无法判定异议依据"
}
```

### 6.2 首批建议建立的机制族

| 机制族 | 反复动作 | 适合题材资源 | 常见漏洞 |
|---|---|---|---|
| 权限交换 | 用一项权限换另一项访问 | 签字权、通行证、席位 | 权限只是换名积分 |
| 资源分配 | 把有限资源分给地点或角色 | 氧气、床位、电量、水配额 | 存在无脑最优解 |
| 证据资格 | 质证来源、程序或保管链 | 异议次数、陈述时间 | 证词只是复述文档 |
| 限时通讯 | 在暴露前发送或验证消息 | 时间窗、暗号次数 | 失败直接断线卡局 |
| 承诺契约 | 作出可被后续验证的承诺 | 保证名额、担保额度 | 承诺没有违约后果 |
| 非对称信息 | 选择交换、公开或保留信息 | 私人频道、阅览资格 | 不分享信息成为最优策略 |
| 空间访问 | 选择打开、封锁或放弃区域 | 钥匙、供电回路、通行许可 | 地图只是章节菜单 |
| 公众叙事 | 决定公开内容和呈现顺序 | 剪辑权、播出时长、热搜位 | 退化成支持率数值 |
| 替代与牺牲 | 用一项资格替代另一项 | 替补名额、撤离座位 | 牺牲没有后续读取 |
| 记忆重构 | 选择恢复、公开或覆盖片段 | 可恢复片段、读取次数 | 记忆被当成客观真相 |
| 竞价与交换 | 用真实筹码争夺稀缺机会 | 席位、物资、承诺 | 私下合谋让系统失效 |
| 轮值职责 | 不同角色轮流掌握决定权 | 值班时段、否决窗口 | 轮值不改变实际能力 |

每张卡都只是起点。选中后，向导必须要求作者填写“本作品中的具体版本”，不能把卡片原文直接当成成品机制。

## 7. 多审查器架构

所有审查器输出统一问题格式，但互相看不到其他审查器的结论，避免集体迎合第一份答案。

### 7.1 语义宪章审查器

只检查锁定事实、权限边界、角色能力、时间线和事件唯一性。

可由程序先检查结构化引用，再由独立语言模型检查自然语言是否与锁定事实冲突。它不评价故事精彩程度。

### 7.2 状态与资源模拟器

完全使用确定性程序。它遍历每章选项，并按状态快照去重：

1. 从初始状态和资源开始；
2. 找到当前满足进入条件的章节变体；
3. 对每个可选项生成下一状态；
4. 拒绝类型错误、越界消耗和未登记引用；
5. 对相同状态快照合并路径；
6. 到终局后匹配结局优先级；
7. 输出最短复现路径。

必须检查：

- 每条结局是否可达；
- 是否有状态值永远不可达；
- 资源是否必然提前耗尽；
- 使用资源后是否反而破坏目标结局条件；
- 选项写入是否被后续读取；
- 两个选项是否最终完全等价；
- 多结局同时命中时是否有明确优先级；
- 是否存在没有任何可执行动作的死局。

组合数量过大时，模拟器按“章序＋状态＋资源＋解锁集合”做哈希去重，并设置路径上限；达到上限应标记为“覆盖不完整”，不能谎称通过。

### 7.3 证据来源审查器

建立证据溯源图，核心字段包括：

- originalRoot：最初产生信息的真实主体或系统；
- provenanceGroup：保管或产生该证据的来源组；
- commonFailureDomain：可能同时污染多份证据的共同故障域；
- originActorKey：最初提供信息的主体；
- collectionMethod：玩家如何取得；
- derivedFromEvidenceKeys：派生关系；
- supportedClaimKeys：它声称支持的结论。

独立性不能只比较 `sourceType`。同一服务器的日志和镜像、同一人的证词和日记、同一文件的截图和打印件都不能自动算作双源。

### 7.4 对抗玩家审查器

复用现有 AI 玩家试跑框架，增加三种专用人格：

- 收益最大化者：始终选择当前看起来收益最高的选项；
- 不合作玩家：拒绝公开秘密、拒绝主动消耗公共资源；
- 规则攻击者：寻找无限循环、免费收益、越权操作和主持解释漏洞。

它只读取玩家在该时点可见的信息，不能提前读取作者真相。完成独立席位推演后，再由观察员对照真实结构生成问题。

### 7.5 机制审查器

只回答：

- 玩家每轮实际做什么；
- 机制是否至少使用两次且每次局面不同；
- 输入、操作、反馈、代价是否完整；
- 成功与失败是否都产生新局面；
- 是否只是换名的投票、信任值或行动点；
- 是否存在明显碾压其他选项的策略；
- 机制是否真正依赖题材。

### 7.6 编辑审查器

最后检查高概念兑现、动机、人物弧光、文风、模板感和扩写价值。它的输出永远是“编辑建议”，不能自动阻止保存，也不能自动改稿。

## 8. 统一审查报告

```json
{
  "id": "finding-001",
  "reviewer": "state-resource-simulator",
  "severity": "blocker",
  "title": "真人重赛路线不可达",
  "claim": "第三章结束前复核席位必然耗尽，但真人重赛要求至少剩余一个席位。",
  "evidenceRefs": ["chapter-1.option-a", "chapter-3.publicEffect", "ending-rematch"],
  "reproductionPath": ["chapter-1.option-b", "chapter-2.option-a", "chapter-3.option-c"],
  "confidence": 1,
  "suggestedDirection": "把席位消耗挂到具体申请选项，或修改结局条件。",
  "autoFixAllowed": false,
  "authorResolution": "open"
}
```

严重度定义：

- blocker：状态不可达、时间线互斥、规则被自身选项破坏、引用不存在等确定性错误；
- must_fix：高度可能破坏可玩性或公平性；
- review：需要作者判断的语义、动机或题材问题；
- suggestion：编辑和风格建议。

作者可以选择：已修复、接受建议、暂缓、带理由豁免。豁免不会删除问题，而是和作品版本一起留档。

## 9. 不允许审查器直接改稿

只有以下机械错误可以生成候选补丁：

- 缺失或错误的 key 引用；
- 数字与字符串类型不一致；
- 未登记资源；
- 明确的重复字段；
- 导出器漏显字段。

即使是机械补丁，也必须显示修改前后差异并由作者确认。

高概念、动机、人物责任、证据设计、结局条件和机制选择不得静默自动修改。

## 10. 调用频率与成本控制

不需要作者每输入一个字就调用六个模型。

### 实时检查（免费、确定性）

在作者保存字段时运行：key、类型、资源上下限、重复选择、未读取状态、缺失反馈、内部状态词泄露等检查。

### 章节检查点（中等成本）

完成一章或一次机制改动后运行：状态模拟器、证据来源审查器和一个对抗玩家。

### 进入扩写（完整复核）

运行全部确定性审查器、三类对抗玩家、机制审查器和编辑审查器。多个独立 AI 审查可以并发执行，最终只聚合相同问题，不让它们互相说服。

### 发布前复核

基于冻结版本再次运行确定性审查和深度玩家试跑。若内容版本未变化，可以复用先前 AI 审查结果。

## 11. 适合织幕现有系统的落地方式

现有能力可以直接复用：

- “创作宪法”保存作者意图和不可破坏原则；
- “作品诊断”已经具备可定位的确定性问题报告；
- “AI 玩家试跑”已经采用隔离玩家上下文和观察员汇总；
- V2.4 大纲结构已具备状态、资源、证据来源、时间线和责任链字段；
- “协作者审稿”可保存人工批注、状态和版本对比。

需要新增四层：

1. 机制设计七问和机制卡片库；
2. 状态／资源全路径模拟器；
3. 证据溯源图与独立性审查；
4. 统一审查收件箱，把程序问题、AI 问题和人工批注合并展示。

## 12. 开发顺序

### M1：新人机制向导

- 七问自然语言表单；
- 首批 12 个机制族；
- 可玩循环预览；
- 反例提示；
- 保存为世界设置，不要求生成完整剧本。

### M2：确定性复核

- 状态注册表；
- 资源注册表；
- 章节读写；
- 结局可达性；
- 路径复现；
- 证据来源图。

### M3：独立 AI 审查器

- 不合作玩家；
- 收益最大化玩家；
- 规则攻击玩家；
- 机制审查；
- 编辑建议。

### M4：复核工作流

- 统一问题收件箱；
- 作者处理状态和豁免理由；
- 版本冻结；
- 仅对变更部分重跑；
- 进入扩写和发布门禁。

## 13. V1 验收标准

新人作者在不接触 JSON 的情况下，应能在 15～30 分钟内：

1. 完成七问；
2. 选择并改造一张机制卡；
3. 看到至少两轮“动作—反馈—代价”；
4. 连接两条早期选择到结局的因果链；
5. 运行一次确定性模拟；
6. 根据可复现问题完成一次修改；
7. 明确区分“程序确认的错误”和“AI／编辑提出的建议”。

只要平台能稳定做到这一点，就已经比“让 AI 一次性生成完整大纲并自我宣告通过”可靠得多。
