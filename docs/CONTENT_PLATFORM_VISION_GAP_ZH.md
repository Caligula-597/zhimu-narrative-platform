# 剧本杀内容平台愿景与差距评估

最后更新：2026-07-06

## 一句话结论

一个完整的线上剧本杀内容平台，不应只把剧本文本搬到三端，而应覆盖：

```text
内容生产 -> 质量检查 -> 上架分发 -> 开局运行 -> 玩家体验 -> 主持控场 -> 复盘沉淀 -> 数据迭代 -> 商业交付
```

当前项目已经具备“可运行的剧情操作系统”内核：三端拆分、规则引擎、线索发放、主持干预、玩家阅读、复盘、内容包导入和 Matrix 内容生产管线都已成型。

真正的差距不在“能不能跑一场”，而在三件事：

1. Matrix 管线产物还没有稳定编译进统一的运行态段落单元。
2. 投票、指认、阵营、秘密行动等社交博弈层仍明显不足。
3. 玩后数据尚未反哺创作者，内容迭代仍缺产品化闭环。

## 阶段判断

| 阶段 | 当前判断 | 说明 |
|---|---|---|
| Phase 0：能跑一场 | 基本达到 | 创作、开房、角色绑定、玩家阅读、线索、主持推进、复盘已有闭环 |
| Phase 1：创作者能控质量 | 局部达到 | Matrix 内部具备公平性、剧透、可主持性、可读性等检查，但未成为每个世界的常驻产品能力 |
| Phase 2：动态博弈 | 尚未达到 | 缺投票、指认、阵营、秘密交易、通用行动 DSL、玩家证据板 |
| Phase 3：平台化运营 | 部分具备 | 有 catalog、plaza、计费骨架和试点 SOP，但授权、销售、数据分析、客户成功仍不足 |

## 三端愿景

### 创作者端

创作者端的目标不是简单写文本，而是把一个故事变成结构化、可检查、可运行的内容包。

| 愿景功能 | 当前状态 | 关键差距 |
|---|---|---|
| 剧情段落编辑 | 部分具备 | 有分幕编辑、章节公开环境、Matrix 情绪字段；缺统一 Segment 实体，目标和情绪未与运行态绑定 |
| 角色视角管理 | 部分具备 | 有角色 script sections 和角色×幕矩阵；缺同一段落下多视角 diff 编辑器 |
| 线索绑定 | 基本完成 | 有线索、可见性、发放和审计；证据链仍偏前端推导，缺专用聚合 API |
| 任务与行动设计 | 部分具备 | Matrix 有 actTasks，但未进入玩家端和运行态 API |
| 真相与误导结构 | 部分具备 | truth bible、info-matrix、truth reconstruction 已在管线内；缺独立 truth bible UI |
| 节奏与强度控制 | 部分具备 | 有评价字段和章节状态；缺幕级强度标记、信息过密、角色太闲提示 |
| 公平性检查 | 部分具备 | Matrix 内较强；普通世界上架检查仍偏基础 |
| 主持提示生成 | 创作侧完成 | host runbook 已生成；主持端未完整消费 runbook 卡片 |
| 试玩模拟 | 部分具备 | 有角色预览和测试房；缺规则、线索、探索联动模拟 |

### 主持人端

主持人端应像导演控制台，核心是节奏、状态、补救和现场安全。

| 愿景功能 | 当前状态 | 关键差距 |
|---|---|---|
| 当前阶段总览 | 部分具备 | 有玩家表和公开环境；缺当前幕/阶段 FSM 一屏总览 |
| 一键推进 | 部分具备 | 可处理待确认事件和规则触发；缺“进入下一幕”按钮 |
| 角色状态看板 | 基本完成 | 阅读、线索、卡住检测已具备 |
| 主持话术卡 | 部分具备 | 只显示部分公开环境；Matrix per-act runbook 未进主持 UI |
| 线索发放控制 | 基本完成 | 手动和规则发放能力已具备 |
| 异常补救 | 部分具备 | 有 checkpoint、nudge、卡住启发式；缺一键补救包 |
| 节奏提醒 | 部分具备 | 有 stuck 检测；缺幕计时器和讨论轮建议 |
| 互动事件触发 | 基本完成 | 有延迟事件、广播、解锁、小游戏；缺短信、电话等叙事事件类型 |
| 投票与选择管理 | 缺失 | 缺 vote API、schema 和 UI |
| 复盘素材沉淀 | 基本完成 | recap 和叙事复盘能力已具备 |

### 玩家端

玩家端的目标不是“读完文档”，而是持续知道自己是谁、知道什么、能做什么、怀疑什么。

| 愿景功能 | 当前状态 | 关键差距 |
|---|---|---|
| 个人剧本阅读 | 基本完成 | 分幕阅读和图片页阅读器已具备 |
| 下一步行动提示 | 部分具备 | 有启发式 actions hub；未接 Matrix actTasks |
| 个人任务清单 | 缺失 | 任务只在 Matrix 导出和文档里，玩家端无任务 Tab |
| 线索库 | 基本完成 | 线索、分享、笔记、已读已具备 |
| 角色关系图 | 缺失 | 只有关系文本字段，无图形化 UI |
| 时间线/事件轴 | 部分具备 | 复盘和后端日志有基础；局中无个人推理时间线 |
| 推理笔记 | 部分具备 | 有高亮、线索备注、notebook API；缺独立推理笔记 Tab |
| 交流与私聊 | 基本完成 | 语音、广场、好友、私信已有；玩家到主持人的私密文字通道偏弱 |
| 沉浸式资料 | 部分具备 | 支持图片、音频、R2 资产；缺环境音、场景视频层 |
| 阶段提交 | 部分具备 | 有读完、调查、小游戏提交；缺投票、指认、秘密行动 |
| 回顾与复盘 | 基本完成 | 玩家视角复盘已有；缺“你的选择如何影响结局”的结构化反馈 |

## 九层能力模型

### 1. 内容质量层

这一层决定内容是不是“可玩”，不是只检查文本是否存在。

| 能力 | 当前状态 | 建议方向 |
|---|---|---|
| 逻辑一致性 | 部分具备 | 将 Matrix evaluate 从试点流程扩展到上架门禁 |
| 信息公平性 | 部分具备 | 将 innocent inference 摘要产品化 |
| 剧透风险 | 部分具备 | 将 killer guard 和 spoiler gates 纳入常规发布流程 |
| 角色戏份均衡 | 部分具备 | 增加字数、任务、线索、屏幕时间均衡分析 |
| 情绪曲线 | 部分具备 | 建立幕间情绪曲线和强度视图 |
| 可主持性 | 部分具备 | runbook 必须进入主持端 |
| 可读性 | 部分具备 | 将段落长度、任务可见性、关键信息埋藏风险纳入检查 |

### 2. 结构化世界观层

这一层把剧本从文本变成可查询世界。

| 能力 | 当前状态 | 建议方向 |
|---|---|---|
| 人物档案库 | 基本完成 | 继续把动机、谎言、秘密、暴露阶段结构化 |
| 地点系统 | 基本完成 | 加强地点与阶段、线索、事件的关联 |
| 物品系统 | 基本完成 | 完善物品状态流转和持有人历史 |
| 事件时间线 | 部分具备 | 统一创作时间线和运行 timeline logs |
| 关系网络 | 部分具备 | 建立专用社交关系图，而不是依赖文本关系 |
| 真相链 | 部分具备 | 将 truth reconstruction 变成可查询、可审计结构 |

### 3. 动态运行层

这一层决定内容能否根据玩家行为自然推进。

| 能力 | 当前状态 | 建议方向 |
|---|---|---|
| 条件触发 | 基本完成 | 继续保持规则引擎作为运行内核 |
| 分支剧情 | 部分具备 | 建立玩家选择分支树和可视化编辑 |
| 延迟事件 | 基本完成 | 增加叙事型事件模板 |
| 隐藏状态 | 部分具备 | 为 player state variables 增加类型化 schema 和 UI |
| 玩家行动系统 | 部分具备 | 建立通用行动 DSL：调查、提交、交换、指认、保护、销毁 |
| 主持人覆盖权 | 基本完成 | 保持所有覆盖行为可审计 |

### 4. 社交与博弈层

这是剧本杀区别于互动小说的核心层。

| 能力 | 当前状态 | 建议方向 |

## 理想段落单元

当前最大结构问题是：故事、机制、运营三层分散在不同系统中。

理想的段落单元应包含：

| 字段 | 说明 | 当前差距 |
|---|---|---|
| 段落名称 | 幕、章、场景或阶段标题 | 当前散落在章节 title 和分幕里 |
| 剧情目标 | 这一段希望玩家理解、感受或完成什么 | Matrix 有 objective，未进运行态 |
| 公开信息 | 所有人或主持人可见的信息 | 已有 publicEnvironment |
| 角色私密信息 | 不同角色在该段看到的版本 | 已有 role script sections |
| 可用线索 | 该段可发现、可发放、可分享的线索 | 有线索和规则，但非段落内嵌 |
| 玩家任务 | 公开任务、秘密任务、可选任务 | Matrix 有 actTasks，玩家端缺失 |
| 主持人提示 | 开场、转场、卡点、补救话术 | Matrix 有 runbook，主持 UI 缺 |
| 触发条件 | 何时开放该段或该段内事件 | 在规则层，非段落层 |
| 结束条件 | 读完、投票、线索公开、主持确认等 | 缺显式 endCondition |
| 异常补救 | 玩家掉队、关键线索遗漏、提前破案等处理 | 缺段落级补救模板 |
| 复盘记录 | 该段实际发生了什么，谁做了什么 | recap 和 timeline 已具备基础 |

建议将段落单元定义为三层：

```text
故事层：发生了什么，玩家应该感受到什么
机制层：谁能看什么，谁能做什么，什么条件触发什么
运营层：主持人如何控场，出问题如何补救，结束后如何复盘
```

## 五个最关键断层

按“已有数据但未接通”的收益排序：

| 优先级 | 断层 | 现状 | 建议桥接 |
|---:|---|---|---|
| 1 | Matrix -> 运行态编译 | actTasks、runbook、mechanicalTriggers 仍主要在 JSON/matrixSync | 导入时写入可查询字段；玩家端下发 tasks；主持端展示 runbook 卡 |
| 2 | 段落单元统一 | 章节、分幕、规则、runbook 分散 | 定义 Segment schema，包含故事/机制/运营三层 |
| 3 | 投票/指认阶段 | vote API、schema、UI 缺失 | 最小 MVP：秘密投票、公开结果、规则触发 |
| 4 | 质量检查产品化 | 主要存在于 wizard/试点脚本 | 世界上架时跑 publish readiness、innocent inference、spoiler/fairness 摘要 |
| 5 | 玩后数据反哺 | recap 有，analytics 弱 | 从 reading_progress、clue_ownership、feedback 生成创作者洞察面板 |

## 推荐路线图

### P0：把内容管线接入运行态

目标：Matrix 产物不再停留在 JSON 和文档，而是能被主持端和玩家端直接消费。

交付：

- Segment schema 草案。
- Matrix 导入时生成 segment、tasks、runbook、endCondition。
- 玩家端任务 Tab。
- 主持端 runbook 卡片。
- 段落级异常补救模板。

### P1：补齐剧本杀核心博弈

目标：让平台从“剧情阅读+线索”升级为“推理、指认、选择、阵营”。

交付：

- 投票/指认 API、schema、玩家 UI、主持结果页。
- 阵营和隐藏身份运行时支持。
- 秘密行动提交。
- 玩家证据板和怀疑度系统。
- 口供提交与矛盾标记。

### P2：把质量检查产品化

目标：每个准备上架的内容都能得到稳定、可解释的质量报告。

交付：

- 上架前质量报告。
- 公平性、剧透、可主持性、可读性、角色均衡评分。
- 质量问题定位到段落、角色、线索。
- 创作者修订建议。

### P3：建立数据迭代闭环

目标：每一场真实游玩都能帮助内容变好。

交付：

- 段落完成率。
- 线索命中率。
- 玩家怀疑变化。
- 主持卡点记录。
- 玩家满意度。
- 玩后自动改进建议。

### P4：平台化和商业化

目标：内容可以被审核、上架、授权、销售、复用和运营。

交付：

- 内容标签和适配配置。
- 版权与授权字段。
- 房间模板。
- 主持培训模式。
- 内容销售与分成。
- 官方活动和评价体系。

## 最终判断

当前项目已经具备很强的底座：运行引擎、三端拆分、线索系统、主持干预、复盘和 Matrix 管线都不是浅层能力。

接下来最重要的不是继续堆更多孤立功能，而是把它们收束成一个统一的内容运行模型：

```text
把文本变成结构；
把结构变成可运行段落；
把每次运行变成下一版内容的证据。
```

只要 Segment 单元、投票/指认、质量检查产品化和玩后数据反哺这四件事打通，平台会从“能跑剧本杀”进入“能持续生产、运营、优化剧本杀内容”的阶段。
