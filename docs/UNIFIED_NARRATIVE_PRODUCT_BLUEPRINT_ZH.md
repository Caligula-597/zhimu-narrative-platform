# 织幕统一叙事产品蓝图：Creator / Host / Player 三端与剧本杀 / 跑团双模式

最后更新：2026-07-24
状态：功能阶段总设计，作为下一轮需求拆解、领域建模和三端验收的共同基线。

逐模块落地、兼容策略和部署顺序见：[UNIFIED_NARRATIVE_IMPLEMENTATION_PLAN_ZH.md](./UNIFIED_NARRATIVE_IMPLEMENTATION_PLAN_ZH.md)。

## 1. 产品结论

织幕不应继续被设计成“创作者后台、主持后台、玩家页面”三个互相拼接的产品，也不应为剧本杀和跑团复制两套业务代码。

推荐的产品结构是：

```text
可编辑作品草稿
  → 不可变发布版本
  → 运行实例（单局房间或长线战役）
  → 场次 / Session
  → 权威事件日志
  → Creator / Host / Player 各自的权限投影
  → 复盘、洞察和下一版修改
```

同一个叙事内核承载两种玩法配置：

- 剧本杀：固定角色、分幕阅读、搜证、线索推理、私密目标、指认与结局。
- 跑团：玩家角色卡、章节与场景、HO、判定/掷骰、NPC、阵营/威胁、长线状态与场次记录。
- 混合模式：只允许组合已经存在的能力，不单独形成第三套数据模型。

当前代码已经拥有世界、角色、章节、私人分幕、场景、线索、调查点、物品、运行段落、规则、房间、事件、主持操作、玩家进度、存档、复盘和审稿等主要底座。真正缺少的不是继续堆按钮，而是四个统一模型：

1. 完整发布版本，而不是让运行房直接读取不断变化的创作草稿。当前已具备不可变 Release、建房预绑定和三端兼容状态提示，但 RuntimeContentProvider 尚未全面启用，绑定 Release 的房间仍明确标记为兼容读取。
2. 统一的玩家知识与可见性投影。
3. 跑团专属的角色卡、判定、战役和场次模型。
4. 三端围绕同一“当前状态 / 下一步行动”的产品表现。

## 2. 不可破坏的产品原则

1. **草稿与运行隔离**：作者修改草稿，不能静默改变正在进行的房间。
2. **服务端决定可见性**：玩家不能收到其他角色秘密后再由前端隐藏。
3. **运行状态只有一个权威来源**：数据库状态与事件日志为准，SSE 只负责通知刷新。
4. **Host 永远可以人工接管**：跳过、补发、撤回、改条件、手工判定和恢复都必须可用且可审计。
5. **AI 只产生草稿**：生成、结构识别和检查结果必须由作者确认后才能发布。
6. **一个对象只有一个主要编辑位置**：其他页面只显示摘要和深链，避免重复编辑产生冲突。
7. **重度编辑使用完整页面**：长文、角色档案、图谱、规则和主持手册不放在居中小弹窗中；弹窗只用于确认和极短快捷操作。
8. **界面使用用户语言**：不向作者暴露 `Segment`、`truth claim`、`hostTruth` 等内部字段名。
9. **玩法差异来自配置和领域扩展**：共享身份、资产、版本、房间、事件和权限；不把跑团做成换词版剧本杀。
10. **先完成可跑闭环，再扩平台功能**：公开广场、社交和市场不能挤占创作—开团—复盘主链的优先级。

## 3. 四层产品数据模型

### 3.1 作品草稿（Project Draft）

对应当前 `world` 及其创作对象，是作者和协作者持续编辑的工作区。

包含：

- 作品定位、玩法类型、适龄与商业档案。
- 世界设定、事实、时间线、人物关系、地点与结局。
- 角色模板、私人内容、角色弧光与可见信息。
- 章节、场景、运行章节、线索/HO、物品、任务、规则和主持手册。
- 素材、审稿意见、修改建议和草稿版本。

### 3.2 发布版本（Release Snapshot）

发布版本是某一时刻可开团内容的完整、不可变快照。

必须包含：

- 所有运行所需对象及引用关系。
- 可见性策略和初始发放策略。
- 规则、小游戏、判定和主持手册版本。
- 素材清单及内容哈希。
- 发布检查结果、作者确认人和发布时间。

运行房绑定一个明确的 `releaseId`。作者发布新版本后，已有房间只显示“有新版本可用”，由 Host 查看影响范围后选择是否升级；不允许自动覆盖。

### 3.3 运行实例（Run）

运行实例有两种形态：

| 形态 | 剧本杀 | 跑团 |
|---|---|---|
| 单局房间 | 一次完整开本 | One-shot |
| 长线战役 | 可选，多次续跑 | Campaign，包含多个 Session |

运行实例保存玩家席位、角色实例、当前场景/章节、已知信息、物品、变量、任务、规则执行、投票、私密行动、检查点和复盘。

### 3.4 事件与投影（Event + Projection）

每次有效运行操作同时产生：

1. 业务状态变化。
2. 审计记录。
3. Room Event / Outbox 事件。
4. 面向不同受众的安全投影。

Creator、Host 和 Player 不直接共享一份大对象，而是读取同一权威状态的不同投影。

## 4. 统一领域对象与玩法映射

底层对象名应保持稳定，界面按玩法类型切换词汇和字段。

| 统一对象 | 剧本杀界面 | 跑团界面 | 说明 |
|---|---|---|---|
| Project / World | 剧本 | 模组 / 战役 | 可编辑作品草稿 |
| Release | 发布版本 | 模组版本 | 可运行的不可变内容 |
| Run | 房间 / 场次 | 团 / 战役 | 实际运行实例 |
| Session | 当局阶段 | 场次 | 一段有开始和结束的运行 |
| Role Template | 角色 | 预设 PC | 创作时的角色模板 |
| Character Instance | 玩家角色 | PC | 某个运行实例中的角色状态 |
| Act | 公共幕 | 章节 | 大结构单元 |
| Scene | 场景 | 场景 / 遭遇 | 玩家当前可以行动的空间 |
| Run Segment | 主持流程段 | 场景流程 | 聚合一段可主持内容；UI 不显示 Segment |
| Information Card | 线索 | HO / 信息卡 | 可以被授予、阅读、分享的信息 |
| Private Content | 角色本 / 私人分幕 | 私人背景 / 秘密信息 | 仅指定玩家可见 |
| Objective | 个人任务 | 目标 / 任务 | 推动玩家行动 |
| Rule | 自动化规则 | 触发规则 | 条件与动作 |
| Check | 小游戏 / 机制判定 | 技能检定 / 对抗 | 有输入、结果和主持裁定 |
| Item | 道具 | 物品 / 装备 | 可拥有、使用、转移 |
| Truth Fact | 谜底事实 | 世界事实 / KP 秘密 | Host 与作者的权威事实 |

现有数据库表无需为改名而大规模重命名。先在领域 service、JSON Schema 契约和前端术语层建立稳定门面，再逐步迁移内部结构。

## 5. Creator 创作者端完整信息架构

创作者端采用七个直白阶段，不再使用“灵魂、骨架、血肉”等诗化导航。每一阶段只保留一个主要工作目标、一个主编辑器和明确的下一步。

### 5.1 阶段一：作品定位

目标：回答“这是什么、给谁玩、怎么玩、预计多长”。

必填字段：

- 作品名、封面、一句话简介。
- 创作类型：剧本杀 / 跑团 / 互动叙事。
- 运行形态：单局 / 长线。
- 玩家人数最小值、推荐值、最大值。
- 单场预计时长、预计场次数。
- 题材、体验标签、难度、主持难度。
- 适龄范围、内容警示、安全边界。
- 作者、版本、版权来源、备案与自审信息。

玩法扩展：

- 剧本杀：本格/变格、推理/情感/机制侧重、固定角色数量、是否允许反串或角色替补。
- 跑团：规则系统、骰制、预设角色或玩家自建、One-shot/Campaign、升级方式。

页面结果：作品概况卡、预计体验、发布档案和下一步缺项。复杂设置进入全页“作品设置”，不在创建向导里一次填完。

### 5.2 阶段二：世界与谜底

目标：建立作者与主持人共同认可的权威事实。

共享能力：

- 公共前提、世界规则、地点、阵营、NPC。
- 事实卡：标题、事实内容、可信度、可揭示阶段、证据与冲突。
- 时间线：时间、地点、参与者、事件、目击者、真实性和可发现性。
- 人物关系：双方、关系类型、公开/私密层、强度和变化条件。
- 结局状态与关键分支。

剧本杀扩展：

- 案件事实：受害者、实施者、手法、动机、机会、隐藏身份。
- 玩家误解、真实答案、支持误解的证据、纠正误解的证据。
- 不在场证明、矛盾证词、误导与公平推理检查。

跑团扩展：

- 阵营、威胁、秘密、世界时钟、前线与后果。
- NPC 目标、态度、资源、秘密、行动模板。
- 地点关系和可变化世界状态。

原“核诡”统一改为“案件事实”或“核心秘密”；原“真相断言”统一改为“事实卡”。

### 5.3 阶段三：角色与玩家信息

目标：定义每个玩家是谁、知道什么、想做什么、会如何变化。

共享字段：

- 名称、头像、公开身份、私人背景。
- 外在目标、内在需求、秘密、关系、行动倾向。
- 起点、转折、终局的人物弧光。
- 初始信息、初始物品、初始任务。
- 可替补性、玩家注意事项、内容警示。

剧本杀扩展：

- 固定席位、角色本、逐幕私人内容、初始线索、指认资格。
- 凶手知情状态、阵营、秘密任务和结局条件。

跑团扩展：

- 角色卡 Schema：属性、技能、资源、状态、装备、法术/能力和成长记录。
- 预设 PC 或玩家提交角色卡后由 KP 审核。
- 角色卡字段由规则包定义，不把某一个商业规则系统写死在核心数据库。

角色档案和长文必须使用完整页面：左侧角色列表，中间结构化档案，右侧“该玩家当前会知道什么”和引用关系；私人正文另有专注写作视图。

### 5.4 阶段四：剧情结构

目标：把事实与角色组织为可以实际运行的章节、场景和流程。

结构层级：

```text
作品
  └─ 章节 / 公共幕
      └─ 场景
          └─ 主持流程段
              ├─ 玩家目标
              ├─ 主持动作
              ├─ 可揭示信息
              ├─ 可用互动
              └─ 进入 / 退出条件
```

主要视图：

- 章节大纲：顺序、目标、公共摘要、预计时长和推进方式。
- 场景列表/画布：地点、参与角色、开放状态、前置条件和后续分支。
- 时间线：按角色或地点查看事件。
- 结构图：只负责节点与关系，不在画布内塞入全部编辑字段。
- 玩家视角：选择角色与运行时刻，预览其可见内容。

拖拽只用于顺序、位置和连接关系；所有关键操作同时提供列表和键盘可用的替代入口。

### 5.5 阶段五：信息、行动与机制

目标：决定玩家如何获得信息、采取行动和改变状态。

共享对象：

- 线索 / HO：公开正文、主持解释、可见性、来源、触发、关联事实与素材。
- 调查点：所在场景、所需条件、消耗、结果和可重复性。
- 任务：目标、受众、状态、完成条件和奖励。
- 物品：持有者、用途、使用条件、转移和消耗。
- 投票：候选项、匿名性、开放/关闭/公布策略。
- 私密行动：发起人、目标、主持裁定和可见性。
- 小游戏：输入、提示、答案、尝试次数、成功/失败效果。
- 自动化规则：条件树、动作、是否需 Host 确认、优先级和防重复键。

跑团新增：

- 判定模板：属性/技能、难度、优势/劣势、公开或暗骰、成功等级和后果。
- 对抗判定与协助。
- 遭遇/冲突：参与者、顺序、轮次、状态和结束条件。
- 通用骰子表达式与结果日志。

所有机制都必须能绑定一个“剧情目的”：提供信息、改变关系、推进场景、消耗资源、制造选择或进入结局。系统提示孤立机制，但不替作者判断剧情好坏。

### 5.6 阶段六：主持手册

目标：让 Host 在现场不需要回到创作后台查数据。

每个主持流程段包含：

- 本段目标和预计时长。
- 开场描述或主持话术。
- 当前公共状态与主持人所知。
- 玩家应该做什么。
- 应发线索/HO、应开放场景、应检查任务。
- NPC 动作或环境变化。
- 推进条件与可选分支。
- 卡关、过快、缺席、跳关和错误选择的补救方案。
- 可执行的快捷操作。

“主持手册”是运行视图的数据来源，不再只是一个长文本导出物。

### 5.7 阶段七：测试、发布与改本

发布前检查分为三类：

- 阻塞：资源归属错误、玩家无可见内容、必需引用缺失、规则无效、关键内容不可达。
- 警告：阅读量失衡、角色信息差过大、孤立线索、无补救方案、素材缺失。
- 建议：体验节奏和内容完善项，不阻止发布。

完整流程：

1. 选择待发布内容。
2. 运行角色视角和 Host 视角模拟。
3. 查看与上一版本的差异及对现有房间的影响。
4. 创建隔离测试房。
5. 在 Host / Player 双端执行预设测试脚本。
6. 确认后生成不可变 Release。
7. 从真实跑局复盘生成可定位到对象的改本任务。

## 6. Host 主持端完整流程

### 6.1 开团前

Host 选择作品发布版本，创建单局房或长线战役，并完成：

- 房间名、人数、公开状态和邀请码。
- 角色分配方式：玩家自选 / Host 分配 / 随机。
- 剧本杀固定席位检查，或跑团角色卡审核。
- 语音、文字频道和安全工具设置。
- 当前版本、素材、规则、场景和首段可用性检查。
- 一键生成玩家链接并查看入房状态。

### 6.2 临场命令中心

推荐布局：

- 顶部：房间、版本、同步状态、计时器、暂停/结束场次。
- 左侧：玩家状态卡——在线、角色、阅读、线索/HO、任务、状态和最近行动。
- 中间：当前场景与主持流程——目标、话术、应发内容、NPC/环境、推进条件。
- 右侧：待处理队列——规则确认、私密行动、投票、卡关、判定、口供和异常。
- 底部：权威时间线与撤销/补救入口。

Host 必须具备：

- 跳过或完成分幕、章节、任务和场景。
- 解锁、补发或撤回内容。
- 修改条件、变量、角色状态、物品和任务。
- 查看“某玩家现在知道什么”。
- 创建投票、判定、小游戏和私密行动裁定。
- 切换场景、调整节奏、发送广播或定向提醒。
- 临时创建 NPC、HO、场景备注或补救内容；默认只写入当前运行实例。
- 创建 checkpoint、按范围恢复并查看影响预览。

所有覆盖操作必须幂等、事务化、有原因、有审计记录，并明确“系统状态撤回不等于玩家遗忘已经看过的内容”。

### 6.3 跑团专属主持能力

- 场次开始/结束、战役时间和现实日期记录。
- 公开掷骰、暗骰、代掷、难度和结果裁定。
- 场景内 NPC、阵营、威胁和世界时钟推进。
- 遭遇顺序、回合、状态和资源管理。
- 角色成长、奖励、伤势/状态和休整确认。
- Session Zero：角色关系、安全边界、桌规和同意记录。

### 6.4 结束场次

结束时生成：

- 公共总结和下一场钩子。
- 每位玩家个人可见的收获、未完成目标和笔记。
- Host 私人运行记录、覆盖操作和卡点。
- Creator 聚合洞察：不可达信息、等待时长、手工干预、规则命中和流程偏差。

## 7. Player 玩家端完整流程

玩家端继续保留五个主 Tab，但所有 Tab 都围绕“现在做什么”服务。

### 7.1 入场

```text
打开邀请链接
  → 登录或游客身份
  → 查看无剧透房间简介
  → 选角色 / 提交角色卡
  → 阅读安全说明与桌规
  → 等待 Host 开始
```

选择角色时只展示公开身份、体验标签、难度和内容警示，不泄露私人背景。

### 7.2 “现在”

首屏固定回答：

- 我是谁。
- 当前在哪里 / 当前是哪一幕。
- 本阶段目标是什么。
- 我现在可以做的 1～3 个动作。
- Host 是否正在等待我。
- 最近获得了什么新内容。

语音状态、成员在线状态和同步状态在此常驻，但不占据主要叙事空间。

### 7.3 “剧情”

- 剧本杀：角色简介、私人分幕、阅读进度和已解锁内容。
- 跑团：角色卡、背景、能力、状态、成长和私人信息。
- 共同能力：书签、仅自己可见的笔记、内容警示和已读状态。

### 7.4 “调查”

- 当前开放场景、地图或地点列表。
- 可执行调查点及条件。
- 线索/HO 册、物品和附件。
- 分享给全房、队伍或指定角色。
- 来源、获得时间和个人推理笔记。

### 7.5 “行动”

- 当前任务与可提交结果。
- 投票、指认、私密行动、交易和向 Host 提问。
- 剧本杀小游戏与机制操作。
- 跑团检定、掷骰、对抗、遭遇动作和资源使用。

### 7.6 “记录”

- 个人时间线、笔记和未完成事项。
- 场次总结、战役日志和个人成长。
- 结束后按权限展示全局真相、角色结局和精彩片段。

## 8. 三端同步规则

### 8.1 命令、状态和事件分工

```text
用户操作
  → Command API（鉴权、归属、校验、幂等）
  → 同一事务写业务状态 + Audit + Outbox
  → SSE 仅通知“发生了什么”与安全的最小信息
  → 各端按游标拉取自己的最新 Projection
  → 断线后 replay；游标失效时完整 reconcile
```

前端不得把收到 SSE 当成最终业务成功，也不得依赖事件到达顺序直接累加关键状态。

### 8.2 统一同步状态

Creator、Host、Player 顶部使用同一组状态：

- 实时同步。
- 正在重连。
- 轮询兜底。
- 离线只读。
- 有更新待拉取。
- 同步失败，需要人工重试。

同时显示最后成功同步时间；错误 Toast 不能替代持续状态条。

### 8.3 关键事件在三端的表现

| 事件 | Creator | Host | Player |
|---|---|---|---|
| 发布新版本 | 显示发布结果与影响 | 显示“新版本可用”，不自动升级 | 无变化 |
| 玩家加入/离开 | 测试房摘要 | 玩家卡实时更新 | 成员状态更新 |
| 分幕/HO/场景解锁 | 测试观测/跑局统计 | 时间线和玩家知识更新 | 对应 Tab 新内容提示 |
| 玩家阅读/调查/任务完成 | 聚合分析，不泄露私聊 | 玩家状态和待办更新 | 自己获得完成反馈 |
| 投票/判定/私密行动提交 | 局后聚合 | 进入待处理队列 | 显示自己的提交状态 |
| Host 覆盖操作 | 局后审计与洞察 | 立即显示结果与撤回边界 | 按权限收到状态变化 |
| checkpoint 恢复 | 测试记录 | 影响预览、结果和审计 | 强制 reconcile 并提示状态已恢复 |
| 场次结束 | 生成改本任务 | 生成运行报告 | 进入个人复盘 |

### 8.4 可见性模型

建议统一为以下受众，不再由每个功能自定义字符串：

- `creator_only`：作者与编辑。
- `host_only`：作者、编辑和当前 Host。
- `public_room`：当前房间所有人。
- `party`：指定队伍/阵营。
- `role`：指定角色实例。
- `player`：指定用户。
- `postgame`：满足复盘条件后可见。

每次读取都通过服务端 `viewerContext` 计算投影；搜索、导出、SSE、版本比较、复盘和错误响应必须使用同一套规则。

## 9. 跑团不是术语切换：必须新增的能力

当前 `creationType` 和共享术语表只能解决文案，不能构成完整跑团功能。系统中立跑团至少需要：

1. `Campaign` 与多个 `Session` 的层级。
2. 可配置角色卡 Schema、角色实例和成长记录。
3. 通用骰子表达式、判定请求、掷骰结果和主持裁定日志。
4. NPC、阵营、威胁和世界时钟。
5. 临时场景/HO/NPC，只影响当前战役，必要时再回写模组草稿。
6. 场次日志、下次钩子、休整与长期状态。
7. Session Zero、安全边界与桌规。
8. 可选遭遇/顺序管理；不应成为第一批的重型战棋地图编辑器。

第一版跑团应保持“系统中立”：支持自定义字段、通用骰制和用户自建规则包，不内置或复制未经授权的商业规则全文。

## 10. 现有能力复用与新增边界

### 10.1 可直接复用

- 身份、会话、协作者、角色权限和世界归属。
- 世界、章节、角色、私人分幕和创作档案。
- Studio 场景、线索、调查点、物品和剧情边。
- 运行段落、规则、任务、怀疑、口供、投票和私密行动。
- Room、Host/Player API、SSE、Journal、Outbox 和幂等。
- 资产、上传扫描、导入导出、审稿和版本比较。
- Checkpoint、Restore、Recap、Creator Analytics。

### 10.2 需要从 JSON/页面功能升级为领域对象

- 完整 Release Snapshot 与房间版本升级。
- 统一 Knowledge Projection / Visibility Grant。
- 主持流程段与运行时当前段落状态。
- 小游戏模板与判定模板。
- 复盘问题到创作对象的修改任务。
- 资产对角色、场景、线索和发布版本的反向引用。

### 10.3 全新领域

- Campaign / Session。
- Character Sheet Schema / Character Instance。
- Roll / Check / Adjudication。
- NPC / Faction / Threat / Clock。
- Encounter / Turn（第二批跑团能力）。
- Safety Profile / Session Zero Agreement。

## 11. 后端领域边界建议

不以页面命名 service，而按业务不变量拆分：

| 领域 | 主要职责 |
|---|---|
| `project` | 作品草稿、成员、设置和内容 revision |
| `release` | 发布检查、不可变快照、版本差异和运行升级 |
| `narrative` | 章节、场景、角色内容、事实和关系 |
| `knowledge` | 信息卡、可见性、发放、分享和“玩家知道什么” |
| `mechanics` | 任务、规则、小游戏、判定和效果 |
| `campaign` | 长线战役、Session 和长期状态 |
| `character` | 角色模板、角色实例、角色卡和成长 |
| `runtime` | 房间当前状态、场景、段落和参与者 |
| `host-command` | Host 覆盖操作、审计和事务 |
| `player-action` | 调查、阅读、投票、私密行动、掷骰和使用物品 |
| `event` | Outbox、Journal、SSE、游标和重放 |
| `projection` | Creator / Host / Player 聚合读取模型 |
| `recap-insight` | 存档、复盘、运行报告和改本任务 |

路由只负责 schema、身份和 service 调用；service 保证权限、事务和不变量；repository 只负责查询。三端首屏使用聚合 projection，避免每个页面串行拉取十几个接口。

## 13. 推荐实施批次

### 批次 A：统一产品骨架（最高优先级）

1. 固化统一领域词典和玩法 Profile。
2. 创作者导航改为七个直白阶段，清除重复编辑入口和重型弹窗。
3. 定义完整 Release Snapshot 契约和发布影响预览。
4. 定义统一 `viewerContext`、可见性和玩家知识投影。
5. 定义三端 `currentState + suggestedActions + syncState` 聚合契约。

这一批完成前，不应继续扩更多独立小游戏或社交功能。

### 批次 B：完成剧本杀专业闭环

1. 案件事实、时间线、证据链和玩家视角联动。
2. 角色档案、私人分幕和角色知识视图收敛。
3. 主持手册成为 Host 当前段落的直接数据源。
4. 线索可达性、规则解释、发布影响和测试房流程。
5. Host 临场自由、Player 五 Tab 和复盘回写完整验收。

### 批次 C：系统中立跑团核心

1. Campaign / Session。
2. 角色卡 Schema、玩家角色实例和 KP 审核。
3. 通用判定、掷骰、暗骰和主持裁定。
4. NPC、阵营、威胁、世界时钟和长期状态。
5. Session Zero、安全工具、场次日志和成长。

### 批次 D：高级能力

- 遭遇与回合管理。
- 地图、区域和轻量迷雾；不先做重型战棋 VTT。
- 可复用规则包和模板市场。
- 更强的多人协作编辑、分支和合并。
- 运行数据驱动的创作洞察和 AI 辅助改本。

## 14. 功能验收标准

### 14.1 剧本杀黄金路径

```text
导入或创建剧本
→ 完成案件事实、角色、分幕、场景、线索和主持手册
→ 发布不可变版本
→ 创建测试房并邀请玩家
→ 玩家选角、阅读、调查、分享、投票
→ Host 推进、补发、撤回、覆盖和存档
→ 三端断线恢复后状态一致
→ 结束后生成个人复盘和改本任务
```

### 14.2 跑团黄金路径

```text
创建模组或战役
→ 选择系统中立规则配置
→ 建立章节、场景、NPC、HO 和判定
→ 玩家选择预设 PC 或提交角色卡
→ Session Zero
→ KP 开始场次、推进场景、请求判定并裁定
→ 玩家行动、掷骰、记录、获得 HO/物品
→ 结束场次并保存长期状态
→ 下一场从同一战役恢复
```

### 14.3 三端一致性

- 同一命令重试不会重复发放、计分、推进或掷骰。
- 任何玩家读取、搜索、导出、SSE 和复盘都不能越过可见性。
- SSE 重复、乱序、断线和游标过期后最终状态一致。
- 新发布版本不会静默改变活动房间。
- Host 覆盖操作有影响预览、原因、审计和可解释结果。
- Creator 看到聚合洞察，不看到不应暴露的玩家私聊正文。

### 14.4 体验指标

- 新作者从导入/创建到第一个可玩测试房的时间。
- Host 每场需要离开织幕去群聊或表格处理的次数。
- 玩家打开“现在”后仍不知道下一步的反馈比例。
- 关键线索/HO 可达率和角色信息覆盖差异。
- Host 手工补救、规则失败和断线恢复次数。
- 场次完成率、复盘查看率和改本任务关闭率。

## 15. 产品经理视角的取舍

### 15.1 当前最大风险

最大风险不是功能少，而是同时拥有很多能力，却没有一个稳定的发布版本、知识模型和当前行动模型。继续增加页面会让三端更难理解，也会放大前后端不一致。

### 15.2 剧本杀与跑团的推进顺序

不建议同时承诺“完整剧本杀 + 完整跑团”并行上线。推荐顺序是：

1. 先把共享发布、知识、运行和同步内核做好。
2. 用已有能力完成剧本杀黄金路径，因为当前资产最成熟。
3. 再加入系统中立跑团的 Campaign、角色卡和判定三件套。
4. 最后才做遭遇地图、规则包市场等高复杂能力。

### 15.3 应暂缓的内容

- 更多彼此独立的小游戏。
- 重型地图/VTT 和战棋渲染。
- 为每个规则系统写死专属逻辑。
- 在核心闭环稳定前扩大广场、好友和内容市场。
- 把每种数据都画成可拖拽图谱。

### 15.4 第一项真正应该实施的功能模块

下一项不应从某个孤立页面开始，而应实施“发布版本 + 知识投影 + 当前行动”纵向模块：

1. Creator 发布完整 Release。
2. Host 用 Release 创建运行实例并看到当前流程。
3. Player 只收到自己可见的当前内容和建议行动。
4. Host 的解锁/撤回通过统一知识投影同步到 Player。
5. Creator 在测试房看到聚合运行结果并生成改本任务。

这个模块一次贯穿三端，能验证产品模型是否成立，也能为后续剧本杀完善和跑团扩展提供稳定基础。
