# 生产级 SaaS 评估

最后更新：2026-06-30

## 结论

织幕当前评分：**74 / 100**。

这不是一个“小打小闹”的项目。它已经具备生产级 SaaS 的主体骨架：领域后端、三端产品、官网、权限、安全门槛、测试、部署脚本、OPS、监控和文档都已经存在，而且不少后端能力已经走在 UI 前面。

但如果按“可以面向陌生用户大规模公开收费”的标准，当前还差一段生产化收口。最关键的短板是：

- 主应用前端仍有较多 legacy 全局桥接，维护复杂度偏高。
- 关键业务 E2E 和真实生产门槛需要持续稳定通过。
- 备份恢复、告警响应、客户支持和 SLA 还需要真实演练。
- 三端共享 API、错误处理、状态语言、视觉 token 还需要继续统一。

建议定位：

```text
可做小规模真实内测和人工陪跑试点；
不建议立即做大规模公开商用发布；
可以按 4-8 周节奏推进到公开 Beta。
```

## 生产级判断

| 等级 | 标准 | 当前状态 |
|---|---|---|
| Demo | 能演示核心想法 | 已超过 |
| Alpha | 核心功能可跑，但依赖开发陪跑 | 已超过 |
| 可信 Beta | 小范围真实用户可用，有人工支持 | 基本达到 |
| 公开 Beta | 陌生用户可自助完成首次体验 | 接近，需要补自助引导、反馈、E2E |
| 商业试点 | 可承接少量付费/企业试用 | 有基础，需要人工陪跑 |
| 标准商用 SaaS | 可规模化获客、计费、支持、运维 | 未达到 |

## 优势

### 1. 后端扎实

后端不是临时 API 拼接，而是已经按业务域拆分。当前能看到 account、asset、billing、checkpoint、content package、creator、host、player、recap、rules、script bundle、studio、world、OPS 等路由边界。

这对未来运维是好事：故障定位、权限审查、接口扩展、测试补齐都会比单文件堆功能更可控。

### 2. 核心业务不是空壳

项目有真实叙事业务复杂度：世界模板、运行房间、角色私人本、线索、调查点、自动化规则、主持确认、玩家阅读进度、存档、复盘、公开库、导入导出。这些能力已经能支撑“长线互动叙事运营平台”的定位。

### 3. 安全和运维意识早

很多早期项目会等到上线后才补 CSP、上传扫描、告警、metrics、schema、rate limit。织幕已经把这些作为生产门槛写进脚本和文档，这是非常正确的方向。

### 4. 测试密度不错

后端测试覆盖面比较宽，包含权限、规则、存档、导入、账单、上传、会话、错误格式、迁移、复盘等。play/host/e2e 也有测试入口。对一个仍在快速迭代的产品，这是偏强的。

## 短板

### 1. 主应用前端复杂度偏高

`zhimuState` 消费者已经完成分片迁移，`window.zhimuState` 仅在测试/演示诊断下暴露；`window.zhimuDom` 窗口桥已删除；`zhimuViews` 已删除；`zhimuRuntime` shell 的生产者和消费者已迁移到 ESM registry。当前主应用的主要前端复杂度来自其它 UI/格式/会话类窗口服务和三端共享层偏薄。这不是产品设计导致的“冗余”，更多是早期快速把功能跑通后留下的演进成本。

这类问题在大项目里常见，但必须继续清理。否则后续每次改 UI、状态、弹窗、toast、页面切换，都可能牵动隐性依赖。

### 2. 三端共享层还不够厚

创作者端、主持端、玩家端的职责划分是对的，但三端都需要 API 请求、错误处理、状态 chip、session、toast、视觉 token。如果每端各写一套，短期快，长期会让运维和回归成本升高。

### 3. 生产演练还不够

文档和脚本已经准备得不错，但生产级 SaaS 最后看的是演练记录：

- 数据库能不能恢复到新库。
- R2/S3 附件能不能恢复或回收。
- 告警谁收到。
- 事故多久响应。
- OAuth、邮件、上传扫描挂了怎么处理。
- 部署失败如何回滚。

这些需要真实跑过，而不是只写在文档里。

### 4. 商业化闭环仍偏人工

套餐、定价、Stripe、OPS 开通都有底座，但距离标准 SaaS 还需要：

- 套餐权益与配额在 UI、后端、OPS 文档中一致。
- 人工开通、发票、订单、升级、降级有记录。
- 客户成功手册能指导首次导入、首场运行、复盘和扩容。
- 隐私、用户协议、数据删除、导出策略有清晰入口。

## 面向上市的建议

### P0：先把可信内测打稳

- 继续完成 A1 剩余窗口服务收口。
- 固化关键 E2E：创作、开房、玩家加入、主持推进、线索发放、复盘。
- 跑通真实生产门槛：CSP、OTLP、alert、AV strict、OPS token、metrics token。
- 做一次数据库备份恢复演练和一次上传扫描故障演练。
- 抽查权限矩阵：world、room、role、catalog、ops、asset。

### P1：把三端产品体验拉平

- 创作者端：制作总控台继续聚合健康度、风险、下一步建议。
- 主持端：首页继续升级为运行控制台。
- 玩家端：首页继续升级为下一步行动入口。
- 线索管理：保持 clue audit 定位，不扩成完整编排台。
- 规则系统：补 rule debug trace，让规则为什么触发/不触发可解释。
- 三端共享：API、错误处理、session、toast、status chip、tokens。

### P2：商业试点准备

- 明确 Beta、Creator、Studio 等套餐权益和配额。
- 建立人工开通 SOP，Stripe 可后置但账单记录不能缺。
- 完成客户交付包：导入、导出、备份、复盘、支持流程。
- 形成 SLA 草案和值班说明。
- 官网换成真实截图、真实案例或匿名 pilot。

## 运维判断

当前的架构拆分对未来运维是有利的。尤其是：

- 模板世界和运行房间分离，避免运行数据污染创作数据。
- 玩家可见内容由后端推导，不依赖前端隐藏。
- OPS、metrics、health、ready、alert 已有明确入口。
- 路由按领域拆分，有利于事故定位。
- 文档把上线门槛、安全门槛和运维 SOP 分开写，方向正确。

但要达到真正生产级运维，需要补三类证据：

1. **持续绿的自动化结果**：CI、E2E、production-ready、monitoring smoke。
2. **真实演练记录**：备份恢复、告警响应、上传扫描故障、部署回滚。
3. **用户支持记录**：反馈进入、处理、回复、关闭。

## 最终评分解释

为什么不是 85 分以上：

- 前端 legacy bridge 已明显收口，但其它窗口服务仍需继续模块化。
- 真实生产演练证据不足。
- 公开 Beta 的用户自助闭环还未完全闭合。
- 商业支持体系还偏草案。

为什么不是 60 分以下：

- 后端能力和测试覆盖明显扎实。
- 三端与官网已经形成真实产品形态。
- 安全、运维、部署、文档不是空白。
- 产品方向明确，功能不是散乱堆砌。

因此，**74 / 100** 是比较合理的生产级 SaaS 评分：已经值得认真投入上市准备，但必须继续按工程化和运维化标准收口。
