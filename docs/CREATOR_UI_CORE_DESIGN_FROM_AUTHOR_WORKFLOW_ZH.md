# 创作者 UI 核心设计：按真实剧本创作流程搭建

最后更新：2026-07-08

## 设计目标

创作端的核心不是“管理一堆数据”，而是陪创作者完成一部剧本杀作品从灵感到可开房、可交付、可复盘的全过程。

因此，UI 应按真实创作心智组织，而不是按数据库表、后端接口、历史批次组织。创作者进入系统后，应该看到的是：

1. 我现在处在创作的哪个阶段？
2. 这个阶段我应该产出什么？
3. 系统能帮我检查什么？
4. 哪些内容已经可用于玩家端/主持端？
5. 下一步该补什么？

本文以真实剧本创作者流程为主轴，将创作端拆成五个阶段：

1. 灵魂的种子：概念与选题
2. 骨架的搭建：架构与诡计
3. 血肉的填充：剧情与人物
4. 游戏的规则：流程与机制
5. 肌肤的裁剪：撰写与物料

## 总体 UI 框架

建议创作端采用“阶段式工作台 + 专业编辑器”的结构。

### 顶层导航

| 一级区 | 对应创作阶段 | 用户问题 |
|---|---|---|
| 概念 | 第一阶段：灵魂的种子 | 我这个本到底卖什么？ |
| 架构 | 第二阶段：骨架的搭建 | 诡计、关系和时间线是否站得住？ |
| 人物 | 第三阶段：血肉的填充 | 每个角色是否有目标、秘密、弧光和行动线？ |
| 流程 | 第四阶段：游戏的规则 | 玩家怎么玩、DM 怎么控节奏？ |
| 文稿 | 第五阶段：肌肤的裁剪 | 玩家本、DM 手册、线索卡、物料是否可交付？ |
| 测试与发布 | 跨阶段验收 | 能不能开房测试、发布、复盘？ |
| 资产与设置 | 辅助管理 | 素材、成员、权限、商业设置如何管理？ |

### 页面布局原则

每个阶段页面保持同一种骨架：

- 左侧：阶段目录与完成度
- 中间：主要创作画布或编辑器
- 右侧：检查器、建议、引用、冲突提示
- 顶部：当前作品状态、保存状态、发布 readiness
- 底部或浮层：AI 辅助、导入、版本、批量操作

### 加载原则

- 首屏只加载当前阶段 summary。
- 复杂内容按节点懒加载，例如时间线、关系图、长稿、线索图片、质量报告。
- AI 生成、导入、自动布局、发布检查都作为异步任务，显示进度和结果，不阻塞导航。
- 所有阶段允许“先粗后细”：先填一句话、卡片、表格，再逐步展开为完整文稿。

## 第一阶段：灵魂的种子 · 概念与选题

### 创作者真实任务

在动笔前，创作者需要完成：

- 寻找核心灵感。
- 确立一句话梗概。
- 明确核心卖点。
- 判断商业定位：目标用户、时长、类型、形式、发行方式。

### UI 模块设计

#### 1. 灵感池

展示形式：

- 卡片墙：每张卡片是一句话、画面、情绪、诡计或社会议题。
- 分类标签：高概念、社会派、诡计先行、情感沉浸、机制先行、IP/题材。
- 快速记录入口：随手写一句，不要求完整。
- 收藏与合并：多个灵感可以合并成一个项目概念。

关键字段：

- 灵感标题
- 灵感类型
- 核心画面/情绪
- 一句话描述
- 潜在冲突
- 潜在玩家体验

体验优化：

- 新建作品时可以从空白开始，也可以从灵感卡开始。
- 支持“把这张灵感扩写成一句话梗概”。
- 灵感卡不进入正式作品结构，除非用户确认采用。

#### 2. 一句话梗概

展示形式：

- 单独的大输入区，不藏在设置里。
- 模板辅助：
  - 这是一个什么类型的本？
  - 几个什么样的人？
  - 在什么场景？
  - 遇到了什么核心危机？
  - 最大卖点是什么？

建议 UI：

```text
这是一个【类型】本，【人数】个【角色状态】在【核心场景】中，
他们必须【核心目标】，但【最大反转/压力源】。
主打【核心卖点】。
```

检查器：

- 是否说清类型。
- 是否包含人数。
- 是否包含场景。
- 是否包含冲突。
- 是否包含卖点。
- 是否能被市场/监制一句话理解。

#### 3. 核心卖点板

展示形式：

- 3 个主卖点槽位，避免卖点过多。
- 卖点类型：
  - 推理诡计
  - 情感沉浸
  - 机制体验
  - 世界观设定
  - 题材稀缺
  - 商业包装

每个卖点包括：

- 卖点标题
- 玩家感受
- 具体实现方式
- 可宣传表达
- 是否贯穿后续阶段

#### 4. 商业定位

展示形式：

- 分段表单 + 预设选择。

字段：

- 目标玩家：硬核、情感、新手、欢乐、机制、跑团、沉浸演绎。
- 人数：例如 4/5/6/7/8 人。
- 预计时长：轻量 3-4 小时、中量 5-6 小时、城限 7-8 小时。
- 类型：本格、变格、新本格、社会派、情感、机制、恐怖、阵营。
- 发行形式：盒装、城限、独家、线上、商业试点。
- DM 难度：低、中、高。
- 物料成本预期。

检查器：

- 时长和内容体量是否匹配。
- 目标玩家和推理难度是否冲突。
- 发行形式和物料成本是否冲突。

### 当前系统对照

已做：

- `world` 基础信息、封面、简介、目录、标签已存在。
- `world-tags` 和 catalog facets 能承接类型/标签。
- 官网和 beta/商业定位已有部分文案与套餐能力。
- `creator-dashboard` 能做作品状态汇总。

没做或不足：

- 没有独立“灵感池”。
- 没有“一句话梗概”作为核心产品字段和检查对象。
- 核心卖点没有结构化。
- 商业定位没有成为创作决策输入，只是散落在标签、简介、套餐或运营文档中。
- 缺少面向创作者的“这个概念是否成立”的检查器。

做得更多但需要收束：

- 现有系统已经有较重的世界、目录、发布、运营能力，但第一阶段需要的是轻量概念孵化，不应一开始要求用户填复杂结构。

## 第二阶段：骨架的搭建 · 架构与诡计

### 创作者真实任务

这一阶段要完成：

- 设计核心诡计。
- 搭建人物关系网。
- 绘制案件时间线。
- 确保动机、机会、证据、不在场证明自洽。

### UI 模块设计

#### 1. 核诡设计器

展示形式：

- 诡计卡片，而不是普通文本框。
- 每张诡计卡可标注类型：
  - 手法诡计
  - 叙述性诡计
  - 身份诡计
  - 结构诡计
  - 机制诡计

字段：

- 诡计名称
- 玩家误解了什么
- 作者真实答案是什么
- 哪些线索支持误解
- 哪些线索最终纠正误解
- 是否有撒谎风险
- 是否可被公平推出

检查器：

- 是否存在唯一解。
- 是否依赖作者强行解释。
- 是否违反已设定时间线。
- 是否需要新增人物能力或道具。

#### 2. 人物关系网

展示形式：

- 关系图谱 + 表格双视图。
- 节点为角色，边为关系。
- 关系边可叠加类型：血缘、旧识、秘密、利益、情感、仇恨、误会、共犯。

体验设计：

- 系统提示“孤岛角色”：和其他角色关系过少。
- 系统提示“私聊 CP 风险”：只有 1v1 强关系，其他玩家无参与感。
- 显示“黄金配比”：每两个角色之间是否至少有 2 条直接或间接联系。

#### 3. 案件时间线

展示形式：

- 横向时间轴。
- 每个角色一条泳道。
- 事件块可拖拽。
- 关键事件可绑定线索、场景、目击者、不在场证明。

字段：

- 时间点/时间段
- 角色
- 行动
- 所在地点
- 目击者
- 证据
- 是否真实
- 是否可被玩家发现

检查器：

- 凶手窗口是否存在。
- 两个角色是否同一时间出现在不可能地点。
- 目击证词是否冲突。
- 关键行为是否缺少证据链。

#### 4. 架构总览

展示形式：

- 核诡、关系、时间线三者联动。
- 点击诡计可高亮涉及角色和时间点。
- 点击时间点可显示相关线索和误导。

### 当前系统对照

已做：

- `studio` 已有场景、线索、物品、调查点和故事图谱。
- `world_role_relationships` 已经有角色关系底座。
- `world_truth_claims` 能承载真相链。
- `world_segments` 可以承载阶段/段落结构。
- `studio-node references` 能查节点引用。
- 自动布局、故事边、节点位置已经存在。
- 矩阵类 AI 管线已经在处理 truth、characters、info matrix、host runbook、player script。

没做或不足：

- 没有“核诡”作为一等对象。
- 没有诡计公平性检查器。
- 没有案件时间线泳道编辑器。
- 关系网还没有围绕“黄金配比”和玩家参与感做 UX。
- 真相链、关系、线索、时间线之间没有形成创作端可视化联动。

做得更多但需要收束：

- 现有 Studio 图谱已经比较复杂，但它偏内容节点编排，不等同于“案件逻辑骨架”。
- AI 矩阵生成能力很强，但需要把输出落回“核诡/关系/时间线”的可编辑结构，而不是停留在生成结果。

## 第三阶段：血肉的填充 · 剧情与人物

### 创作者真实任务

这一阶段要完成：

- 为每个角色写独立小传。
- 设定外在目标、内在需求、秘密、行动线。
- 设计人物弧光。
- 铺设细节与伏笔。

### UI 模块设计

#### 1. 角色档案

展示形式：

- 角色卡列表。
- 每个角色进入后是结构化档案。

字段：

- 角色名
- 玩家可见身份
- 真实身份
- 外在目标
- 内在需求
- 最大秘密
- 行动线
- 情感关系
- 可公开信息
- 私密信息
- 结尾认知变化

#### 2. 人物弧光编辑器

展示形式：

- 起点 -> 冲突 -> 崩塌/反转 -> 终局 的四段式。
- 每段绑定章节、线索、剧情事件。

检查器：

- 角色是否有起点和终局变化。
- 弧光是否只存在于作者设定里，没有进入玩家剧本。
- 角色是否只有功能身份，没有情感动机。

#### 3. 伏笔管理器

展示形式：

- 伏笔卡片：
  - 埋设位置
  - 表面含义
  - 真实含义
  - 回收位置
  - 涉及角色/线索/场景

检查器：

- 是否有未回收伏笔。
- 是否有关键真相没有前置伏笔。
- 是否有过度明显的提示。

#### 4. 玩家剧本分配预览

展示形式：

- 选择一个角色，预览该玩家在每一幕会读到什么。
- 显示该角色知道/不知道的信息。
- 显示和其他角色的私聊点。

### 当前系统对照

已做：

- `role_slots`、角色 CRUD、私人段落 `script_sections` 已存在。
- `writer.js` 已经接入角色、章节、段落、版本、导入。
- `story-manuscript` 支持长稿。
- `matrix-player-script` 和角色脚本生成能力已存在。
- `content-versions` 支持版本恢复。

没做或不足：

- 角色档案没有完整结构化成“外在目标/内在需求/秘密/行动线/弧光”。
- 人物弧光不是一等 UI。
- 伏笔没有独立管理器。
- 玩家剧本预览还不够以“单个玩家视角”组织。
- 缺少“这个角色是否好玩”的检查器。

做得更多但需要收束：

- 现有文稿/导入/AI 生成能力已经超过基础角色创作需求，但 UI 应先让用户填角色核心，再展开长稿和 AI。

## 第四阶段：游戏的规则 · 流程与机制

### 创作者真实任务

这一阶段要完成：

- 分幕式结构设计。
- 线索系统设计。
- 独特游戏机制设计。
- 让玩家有稳定心流，而不是只读故事。

### UI 模块设计

#### 1. 分幕流程设计器

展示形式：

- 幕结构时间轴：
  - 第一幕：破冰
  - 第二幕：案发
  - 第三幕：深入
  - 第四幕：反转与高潮
  - 终幕：结局与复盘
- 每一幕包含：
  - 目标
  - 玩家可读内容
  - DM 任务
  - 可开放地图/线索
  - 私聊建议
  - 预计时长
  - 推进条件

检查器：

- 某幕是否阅读量过大。
- 是否连续太久没有新线索或新行动。
- 是否缺少破冰或复盘。
- 是否存在玩家长时间无事可做。

#### 2. 线索系统

展示形式：

- 线索库 + 分发矩阵。
- 线索类型：
  - 深入线索
  - 验证线索
  - 误导线索
  - 情感线索
  - 机制线索
- 分发方式：
  - 搜证
  - DM 发放
  - 回忆触发
  - 规则触发
  - 角色持有

检查器：

- 深入线索是否必须可达。
- 误导线索是否过多。
- 关键推论是否有至少两条支撑。
- 某角色是否拿不到有效信息。

#### 3. 机制设计器

展示形式：

- 机制模板库：
  - 私聊规则
  - 拍卖
  - 技能卡
  - 投票
  - 阵营状态
  - 私密行动
  - 小游戏
  - 道具触发
- 每个机制必须绑定剧情目的：
  - 推进诡计
  - 增强沉浸
  - 制造冲突
  - 控制节奏
  - 产生证据

检查器：

- 机制是否只是小游戏堆砌。
- 机制是否影响剧情或推理。
- 机制是否让某些玩家长期失去参与感。

#### 4. DM 节奏预演

展示形式：

- 用主持视角模拟一局。
- 展示每一幕 DM 该做什么。
- 展示过快/过慢/跳关/挂机的处理建议。

### 当前系统对照

已做：

- `automation_rules`、规则 CRUD、规则校验、规则触发已存在。
- `host-routes` 已有主持推进、事件队列、发线索、解锁、催促、日志、规则预览。
- `room_events` 和 SSE 已存在。
- `content-platform` 已有投票、私密行动、阵营状态。
- `batch-b` 已有玩家任务、怀疑度、口供、段落补救。
- `mini-games` 已有小玩法底座。
- 线索、场景、调查点、物品已存在。

没做或不足：

- 没有以“分幕流程”为核心的创作 UI。
- 线索没有按深入/验证/误导/情感/机制进行创作者心智分类。
- 机制没有要求绑定剧情目的。
- DM 节奏预演不够产品化。
- 玩家心流检查器不足，例如等待时间、信息不均、参与感断层。

做得更多但需要收束：

- 后端运行时能力已经非常多，包括投票、私密行动、任务、口供、事件、规则、小玩法，但创作者 UI 还没把它们组织成“流程与机制设计器”。
- 主持端能力比创作端机制设计更成熟，说明系统更会“运行”，但还不够会“帮助作者设计运行”。

## 第五阶段：肌肤的裁剪 · 撰写与物料

### 创作者真实任务

这一阶段要完成：

- 撰写组织者手册。
- 撰写玩家剧本。
- 设计线索卡和道具。
- 控制阅读量和表达质量。
- 形成可交付物料。

### UI 模块设计

#### 1. DM 手册编辑器

展示形式：

- 分幕手册。
- 每幕包含：
  - 流程总览
  - DM 话术
  - 线索详解
  - 扶车建议
  - 复盘解释
  - FAQ
  - 备选方案

检查器：

- 是否每幕都有 DM 话术。
- 是否每条关键线索都有解释。
- 是否每个杠点有 FAQ。
- 是否有玩家跳关/挂机/过快/过慢预案。

#### 2. 玩家剧本编辑器

展示形式：

- 按角色 + 幕切换。
- 每幕阅读量显示。
- 镜头语言检查：
  - 环境
  - 动作
  - 对白
  - 情绪
  - 信息点

体验优化：

- 每幕建议阅读量上限，例如 1500 字。
- 可显示“玩家能否用自己的话复述”的信息密度提示。
- 支持从结构化角色档案生成草稿，再人工润色。

#### 3. 线索卡与道具编辑器

展示形式：

- 线索卡网格。
- 卡片支持文字、图片、附件、可见条件、分发方式。
- 道具清单支持成本、制作状态、替代方案。

检查器：

- 线索文字是否歧义。
- 图片是否承载关键可读信息。
- 道具是否必须，还是可选增强。
- 是否有缺图/缺附件/缺分发规则。

#### 4. 交付包导出

展示形式：

- 玩家本导出。
- DM 手册导出。
- 线索卡导出。
- 物料清单导出。
- 测试房间创建。
- 内容包版本快照。

### 当前系统对照

已做：

- `story-manuscript`、文稿保存、长稿同步已存在。
- `documents/parse/import` 支持文档导入。
- `content-package` 支持内容包导入导出。
- `script-bundle` 有剧本包分析/导入底座。
- `assets` 支持素材上传、下载、删除、恢复。
- `pdf-document`、文档解析、页面导入等后端能力已经存在。
- `recap`、FAQ/复盘相关能力有一部分底座。

没做或不足：

- DM 手册没有作为独立、结构化的一等编辑器。
- 玩家剧本没有足够强的“按角色 + 分幕 + 阅读量”编辑体验。
- 线索卡/道具没有形成真正的物料生产 UI。
- 缺少交付包导出向导。
- 缺少文案质量检查，例如镜头语言、阅读量、信息密度、歧义。

做得更多但需要收束：

- 系统已有大量导入、内容包、资产、PDF/文档处理能力，但最终交付体验还没统一成“可给 DM/玩家使用的一套物料”。

## 跨阶段：测试、发布、复盘

### UI 模块设计

#### 1. 创作完成度

按五阶段给出完成度，而不是只显示技术检查：

- 概念完整度
- 架构完整度
- 人物完整度
- 流程完整度
- 文稿物料完整度
- 运行测试完整度

#### 2. 测试房间

从创作端一键创建测试房：

- 选择人数。
- 选择角色。
- 生成玩家邀请。
- 打开主持端。
- 记录测试反馈。

#### 3. 复盘回写

测试后把问题回写到对应阶段：

- 玩家看不懂某线索 -> 回到线索系统。
- 某角色无聊 -> 回到人物弧光/关系网。
- DM 不知道怎么扶车 -> 回到 DM 手册。
- 玩家卡住 -> 回到流程/机制。
- 推理不公平 -> 回到核诡/证据链。

### 当前系统对照

已做：

- `rooms`、`play`、`host`、邀请、SSE、主持控制都已有。
- `checkpoints`、`recaps`、`feedback` 已有。
- `world-readiness`、`quality-reports`、`segment-remedies` 已有。
- OPS 和反馈处理已经有入口。

没做或不足：

- 复盘问题没有自动回写到创作阶段。
- 测试房间和创作检查没有形成统一闭环。
- 发布 readiness 仍偏技术/内容检查，缺少“真实玩家体验”维度。

## 我们当前做得更多的地方

现有系统已经超过基础创作工具的部分：

1. 运行时后端能力很强：房间、主持、玩家、事件、SSE、规则、检查点、复盘都已具备。
2. 运营能力较多：OPS、反馈、计划升级、告警、监控、审计、beta 申请已经存在。
3. 平台化能力较多：官网、玩家广场、社交、公开目录、catalog、标签 facets 都有基础。
4. AI 管线较深：DeepSeek、矩阵生成、truth、characters、info matrix、host runbook、player script 等已做得比普通创作工具更重。
5. 安全和生产门槛较多：限流、CORS、安全头、上传扫描、OpenAPI、metrics、session、OAuth 等已经有生产化基础。

这些是优势，但它们不能替代创作者第一视角的工作流。现在的问题不是能力不够，而是能力没有被组织成“作者自然会用”的界面。

## 我们当前缺得最关键的地方

按真实创作流程看，最缺的是：

1. 概念孵化层：灵感池、一句话梗概、核心卖点、商业定位检查。
2. 核诡设计层：核诡对象、公平性检查、误解/真相/线索链。
3. 案件时间线：角色泳道、目击、不在场证明、证据链自洽检查。
4. 角色深度层：外在目标、内在需求、秘密、行动线、人物弧光。
5. 伏笔管理：埋设、回收、真实含义、表面含义。
6. 分幕流程设计：每幕目标、时长、DM 动作、玩家行动、推进条件。
7. 线索分类和分发矩阵：深入、验证、误导、情感、机制。
8. DM 手册编辑器：话术、扶车、FAQ、跳关/挂机/过快/过慢预案。
9. 玩家剧本编辑器：按角色和分幕控制阅读量。
10. 物料生产：线索卡、道具、交付包导出。
11. 测试反馈回写：把 play/host/recap 的问题回到创作阶段。

## 最小重构路线

暂时不改原有代码时，建议先把产品设计定成以下顺序。

### Phase 1：新增创作流程壳

只做 UI 信息架构，不重写业务：

- 概念
- 架构
- 人物
- 流程
- 文稿
- 测试与发布
- 资产与设置

旧页面能力先映射到新导航。

### Phase 2：补最缺的三个结构对象

优先新增：

1. 一句话梗概/核心卖点/商业定位。
2. 核诡/证据链/公平性检查。
3. 分幕流程/线索分发矩阵。

这三个会直接改变创作端的专业感。

### Phase 3：把现有能力重新挂载

现有能力映射：

- `studio` -> 架构 + 流程 + 文稿物料
- `writer` -> 人物 + 文稿
- `rules` -> 流程机制
- `director/host` -> 测试与发布
- `archive/recap` -> 测试反馈
- `assets` -> 文稿物料 + 资产设置
- `ops` -> 发布后运营，不放进创作者主流程

### Phase 4：做体验检查器

把系统从“录入工具”升级为“创作教练”：

- 概念检查
- 核诡公平性检查
- 关系网孤岛检查
- 时间线矛盾检查
- 角色好玩度检查
- 分幕节奏检查
- 线索可达性检查
- DM 手册完整度检查
- 玩家阅读量检查
- 物料缺失检查

## 结论

我们现在的后端和部分前端已经做了很多“运行平台”和“内容管理”的能力，但还没有完全变成一个真正懂剧本杀作者的创作端。

下一版创作端的关键不是多加一个按钮，而是把产品心智改成：

> 从灵感、诡计、关系、时间线、人物、流程、线索、机制、文稿、物料，到测试和复盘的完整创作工作台。

如果按这个方向重构，现有系统的大量能力都能复用，而且会第一次形成非常清晰的创作者体验。
