### 本轮顺带修复的问题

- 章节编辑收到失效 `chapterId` 时不再访问空对象并抛错；
- 角色/章节/节点保存均增加防重复提交；
- 平行房切换复用已加载列表，不再为显示名称额外请求一次房间列表；
- 房间与编辑器异步完成时校验当前世界及请求序列，旧世界响应不会覆盖新页面；
- 拖拽连线使用固定终点时不再被通用“目标必填”规则误拦截；
- 重复点击同一种新增节点按钮不再清空当前未保存草稿；
- SSE 刷新后若场景或连线目标已被删除，会要求重新确认有效引用。
- 只读审稿身份不再显示新增、保存、删除、自动排布和拖拽连线入口，选中节点时改为只读详情；
- 旧节点详情保存增加前端防重入，连续点击不会重复发送更新请求。
- 运行房创建成功但后续刷新失败时明确提示“已创建、刷新待恢复”，不再误报创建失败并诱导用户重复建房；
- 创建房间期间切换剧本时，旧世界响应不会把当前上下文切回去。
- 完整母稿双向同步增加显式二次确认，未保存正文不会被编排图静默覆盖；
- 母稿、文档解析、内容包预览/导入和导出均增加防重复提交与跨世界旧响应保护；
- 文档图片导入复用首次解析的 Base64，不再为确认导入重复读取并编码同一文件；
- 内容导入预览绑定文件修订号、文件元数据和导入模式，解决“预览文件 A、改选文件 B、却提交 A”的错写风险；
- 内容包存在阻断性引用错误时不再显示确认导入按钮，避免以“跳过损坏对象”的方式产生残缺世界；
- 新世界导入成功后先切换新世界再刷新，删除一次无意义的旧世界请求；刷新失败会明确提示已提交，避免重复创建；
- 新世界内容包导入使用会话级 `requestId`、所有者范围回放查询和 PostgreSQL advisory transaction lock；响应丢失后的重试会恢复已创建世界，不会再复制一个世界；
- 导出中途失败会列出已经生成的交付物，不再把部分成功统称为完全失败；
- 主持手册导出不再原地排序共享 store 中的 Segment 数组，避免导出动作改变页面顺序；
- 真实内容包导入不再受 Fastify 默认约 1MB 上限误伤；现采用 16MB 明确上限、5,000 实体总量上限、解析前 IP 限流和单实例并发队列，避免简单放大请求上限形成攻击面。
- 保存创作版本不再打开全局小框；新工作区明确展示章节、私人分幕、历史版本和真实恢复边界，并阻止空名称、超长名称、重复提交及跨世界旧响应。
- 创作版本名称在历史列表中统一转义，关闭了由版本名称触发存储型 HTML 注入的前端渲染入口。
- 自动化规则的旧“开始配置”提示弹窗已移除，遗留入口与现有按钮都会直接进入规则工作区。
- 已删除无引用且会重新注入旧 `studioModal()` 实现的历史一次性迁移脚本，避免后续维护者误解或恢复已淘汰架构。
- 协作者审稿已按 model / view / controller 拆分为独立懒加载工作区；意见筛选、新建批注、回复、解决/驳回及版本差异不再争用全局 modal。
- 审稿列表与版本对比增加请求序列和当前世界校验，快速切换筛选、版本或剧本时，旧响应不会覆盖新页面；真相或运行段落来源失败时降级为部分目标可用。
- 新意见与逐线程回复草稿在页面重绘后保留；写入期间阻止离开，写入成功但列表刷新失败时不会恢复已提交草稿并诱导重复发送。
- 审稿正文、回复、目标、版本名称、结构化 JSON 和差异字段统一转义；结构化建议同时执行 JSON 对象、100 字段、32 KiB 的前端与后端双层边界。
- 协作权限已按 model / view / controller 拆为独立懒加载工作区；打开一次只请求一次成员端点，不再分别为成员与待接受邀请重复查询同一接口。
- 邀请、角色变更、移除、重发和撤销均固定携带打开工作区时的 `worldId`；列表刷新校验请求序列，所有异步回写校验当前世界，避免切换剧本后误更新新上下文。
- 角色变更改为显式保存；移除成员和撤销邀请增加页面内二次确认，所有写入阻止重复点击，写入成功但刷新失败时保留本地已提交结果。
- 邮件未配置或发送失败时，新的邀请凭据会在当前权限工作区内提供手动复制入口；成员名、邮箱、剧本名和链接均统一转义。
- 成员角色更新与移除补齐 `world.collaborate` 能力检查，与邀请、重发、撤销保持一致，避免注册账号能力门禁出现旁路。
- 玩家视角模拟已按 model / view / controller 拆为独立懒加载工作区；角色秘密、Player 初始可读分幕、场景、线索和不可见原因在同一阅读上下文中展示，不再占用全局 modal。
- 旧模拟器“所有私人分幕一律展示”的错误已修正：测试稿只在测试房可见，非首幕必须存在运行时解锁记录；父章节发布状态不会虚构成 Player 分幕查询门槛。
- 公开线索不再误报为“进房即见”；Player 实际要求获取或分享记录。场景也按 `room_content_unlocks` 判断，不再把创作 metadata 的开放标记冒充运行态。
- 玩家私人预览权限收紧为 owner / editor / reviewer；host 与 viewer 不再获得查看完整创作私稿的入口。
- 剧情助手已改名为与真实能力一致的“剧情结构提取”，按 model / view / controller 拆为独立懒加载工作台；文本修改会使旧预览失效，写入固定当前剧本并要求页面内二次确认。
- 结构写入成功但后续页面刷新失败时会明确提示“已提交、切勿重复导入”，避免响应链后半段故障诱导重复创建节点；远端结构内容统一归一化、限制数量并转义输出。
- 十个 Writer 全页工具实现已统一使用 `writer-tool-layout.js`；页面标识、返回行为、双栏网格、统计事实和风险说明不再由每个领域重复拼接，后续迁移只需实现领域内容与控制器。
- Host 玩家详情、发线索、发物品、解锁/撤回/跳过分幕、开放场景、提醒、日志、线索备注和移出玩家已迁入页面内工作台；工作台按 model / command service / controller / view 拆分，旧 `host-intervention-controller` 全局 modal 已删除。
- Host 命令写入期间禁止重复提交，固定绑定打开时的 roomId；写入成功但状态刷新失败时会明确提示“已提交、切勿重复操作”。玩家知识视图会随相关 SSE 事件刷新，Player 对线索、物品、分幕、场景和提醒事件均有对应回归契约。
- Host 自动化规则编辑已迁入页面内工作区，按草稿模型、编辑事务、列表命令、控制器和视图拆分；新建、编辑、启停和删除均复用 `membership_role` 权限契约，主持人/审稿人只保留查看与运行预览。
- 规则保存先执行本地边界与服务端引用校验；重复提交被锁定，响应丢失时使用 `metadata.hostRequestId` 从规则列表核对，写入成功但刷新失败不会误报成保存失败。
- Host 复盘与存档创建已迁入页面内归档工作区；两种草稿彼此独立，右侧历史列表提供房间上下文，输入边界与后端 120/2000 字符 schema 保持一致。
- 存档点客户端已补齐后端原有的幂等能力；复盘和存档请求超时由通用 20 秒调整为 45 秒，以覆盖后端 30 秒安全事务窗口。响应丢失时草稿冻结，显式核对会复用同一幂等键。
- Host 归档核对收到 `IDEMPOTENCY_IN_PROGRESS` 或幂等服务暂时不可用时继续冻结草稿和原键，不再错误解锁并诱导重复创建；标题和备注按后端实际 trim 后的 payload 指纹去重。
- Host 登录/选房页不再预载整个监控台；监控台视图、action runtime、布局及三个长工作区样式统一在进入运行房时加载，首屏 JS 从约 53.8 KiB gzip 降至约 24 KiB。
- Host 顶部返回首页、切换房间和浏览器刷新现在共用离开门禁；归档/规则有草稿或核对未完成、现场命令仍在提交时，不再绕过各工作区自己的放弃确认。
- Host 待确认事件的详情、执行、拒绝和延迟统一进入同一个页内审阅工作区；操作固定绑定打开时的运行房与事件，事件被其他主持处理后会在写入前拦截，网络不确定态复用原幂等键核对。
- Host 投票创建不再调用浏览器 `prompt`；标题、玩家提示、投票类型和结果可见性按 Fastify schema 先行校验，后端创建路由新增房间级幂等保护。
- Host 建房不再把“房间已创建”和“列表刷新成功”混为一个事务结果；服务端提交后先本地登记房间和邀请码，刷新失败仍保持成功，断线重试复用数据库创建幂等键，防止重复房间。
- Creator 世界运行日志已按 model / view / controller 拆成独立懒加载工作台；房间、事件和关键词筛选拥有 50–200 条明确读取边界，异步响应校验请求序列与固定世界，日志、房间、用户和事件字段全部转义。
- Writer 最后一份运行日志 modal 模板已删除；母稿、发布影响、玩家模拟、文档解析、导入、导出、剧情结构提取及运行日志均不再通过 Writer 全局浮层实现。

## 结论

当前问题不是三个孤立弹窗，而是三端共同存在的交互结构债务。按“能够触发一次居中遮罩层”的源码入口统计：

| 端 | 浮层触发点 | 应改独立工作页 | 应改侧栏/就地面板 | 可保留短弹窗 |
| --- | ---: | ---: | ---: | ---: |
| Creator / `app.getzhimu.com` | 87 | 28 | 25 | 34 |
| Host | 15 | 1 | 8 | 6 |
| Player | 9 | 0 | 6 | 3 |
| **合计** | **111** | **29** | **39** | **43** |

因此，初筛有 **68 个入口不应继续维持当前居中小框形态**；其余 43 个属于删除确认、状态结果、短选择等事务，可以保留，但需要统一可访问性行为。

这里统计的是“用户入口/触发点”，不是 CSS 类数量。底层实际主要由三套浮层基础设施承载：Creator 全局 `#modal`、Host 动态 `modalEl`、Player 状态驱动 modal。

### 可以保留短弹窗（43）

仅限：

- 删除、撤回、恢复等危险确认；
- 调查结果、规则检查结果、创建成功等短结果；
- 延迟时长、场景选择、版式选择等单一选择；
- 邀请码复制、邮箱验证提示等短事务。

保留的弹窗也必须补齐 `role="dialog"`、`aria-modal`、初始焦点、焦点循环、Esc 关闭、关闭后焦点返回以及背景 `inert`。目前 Player 基础实现相对完整，Creator 与 Host 仍缺少其中多项。

## 结构原因

Creator 的基础 `.modal` 默认宽度只有 `min(520px, 90vw)`。大量领域功能通过 `studioModal()` 或直接向同一个 `#modal` 写入 HTML；功能增长后只是不断扩大高度、增加内部滚动或覆盖特殊 class，没有形成独立页面的信息架构。

这会造成：

1. 所有功能视觉上像同一种 AI 生成表单；
2. 用户失去当前对象、图谱节点、规则引用等上下文；
3. 长表单无法形成章节、步骤、状态与保存反馈；
4. 多层滚动、窄列和固定底部按钮在小屏及缩放场景下容易失效；
5. 同一个全局 modal 被不同领域复用，后续很容易出现 class、事件与焦点状态残留。

## 推荐迁移顺序

1. 建立统一的 `WorkspaceRoute`、`ContextDrawer`、`ConfirmDialog` 三种壳层及选择规则。
2. 第一批迁移截图中的线索编辑、规则编辑、小游戏编辑。
3. 第二批迁移世界/平行房、角色/章节、母稿/导入导出（平行房、角色、章节、母稿、文档解析、内容导入和交付导出已完成）。
4. 第三批迁移编排节点、协作审稿、发布影响、运行段落/事实/关系（编排节点、发布影响已完成）。
5. Host 现场操作层、事件上下文、规则长编辑器、复盘/存档、投票和建房已完成，Creator Director 副本已删除；下一步处理 Player bottom sheet 与 Creator 剩余低频长事务，并删除各批被替代的旧 modal 代码。

验收时不能只检查页面能打开，还要验证深链接、刷新恢复、未保存离开、接口失败、键盘导航、缩放和小屏回流。
