# AI 大纲生成 V2.4：语义宪章、分支执行与生成前创作合同

## 结论

大纲生成现在采用：

> 批次合同预分配 → 创作蓝图 → 章节装配 → 结构/语义回归 → 批次反模板验收

门禁仍然首先是“给生成者看的创作宪法”：AI 必须在写作过程中遵守。与此同时，能够确定计算的规则必须由程序做最终验收，否则“提示词写了”不等于“实际执行了”。

程序不判断作品是否感人、惊艳或高级，也不在旧稿上 patch/rebuild；任何硬门禁失败，当前阶段的草稿直接拒收并重新创作。V2.4 尤其禁止后端替 AI 补写玩家选项、状态值、证据来源、资源消耗或结局条件。

## 为什么不是旧的三轮返工

旧设计是：

1. 生成完整大纲；
2. 后端报告问题，模型 patch 或 rebuild；
3. 仍失败时再次携带旧稿和错误返工。

它的问题是旧稿的模板、弱机制和错误人物结构容易被继承，而且后端会逐渐代替生成者做创作判断。

现在没有“生成—补丁—补丁”三轮。一次完整草稿由两个连续的创作阶段构成：

1. **创作蓝图**：锁定唯一真相、六人责任、题材机制、贡献类型、实体、状态类型、资源用途、结局路线、文风装置和批次指纹。
2. **章节装配**：只补齐六人逐章行动和五章因果节点，让蓝图中的状态、资源、权限、关系和机制真实运行。

第二阶段的模型响应顶层只能包含 `playerChapterActions`、`chapterBeats` 和 `styleChapterExpressions`；程序将这三个数组确定性合并进已验收蓝图。因此模型没有重传真相、机制、状态或结局的入口。任何一阶段失败都不会在旧 JSON 上打补丁，而是从第一阶段重新开始一份新草稿。

## 批次合同：并发开始前先消除重复

40 个请求并发时彼此看不到，所以不能指望模型自行避开同批内容。脚本在发起并发前为每篇预分配：

- 六个按题材时代人工策划的玩家姓名，混合二字名、三字名、字号与代号；
- 题材推进模式；
- 六人的贡献类型组合；
- 专属状态 key，并禁止通用 `state-trust`；
- 题材世界内资源合同，例如合规申诉次数、浮力能源配额、温室水配额、剪辑否决权，而不是统一“决策容量”；
- 专属剧情发动机；
- “缺失/删除/不存在对象”机制维度；
- 真相知情分布；
- 六人关系拓扑；
- 结局名称反模板约束与批次重复检查；
- 文风落地种子。

模型必须逐项执行 `generationContract`，不能自行换回常见名字、万能信任值、NPC 幕后黑手或“恢复被删除记录”的通用结构。

这些批次字段同时以“不可覆盖骨架”随提示词交给模型。合同锁定姓名、贡献类型、聚光章、状态 key/类型、题材资源和批次指纹，但不再替模型创造证据来源、玩家选项或结局条件。模型必须在写作阶段提供真实世界内容；缺失就拒收，而不是由后端补齐。

## 第一阶段：创作蓝图

蓝图必须完成：

- 梗概异常点与真相逐项兑现；
- 用 `cause / escalation / maintenance / resolution` 拆分玩家责任；至少一名玩家承担制造、升级或维持危机的责任；
- 明确 `责任链：` 与 `NPC边界：`，受害者、解谜钥匙和最终裁决者不能冒充危机责任人；
- 用 `causalTimeline` 锁定真实事件发生顺序，避免同一事件既发生在入场前又被第一章重新触发；
- 玩家和 NPC/机构/设备/物证使用不同注册表，禁止同名双重登记；
- 六人按合同承担 evidence、relationship、commitment、authority、resource、task、risk、memory 或 audience 等不同贡献；
- 题材机制写清触发、判定步骤、成功效果、失败代价和能力边界；
- 文风装置逐章落实到场景或对白；
- 状态 key 和类型统一登记，每个枚举值用 `valueSemantics` 声明世界内含义和冲突说法；
- 资源若存在，预先声明最少可选使用章节数、最多公共必然变化次数，并由结局读取；资源不再按固定章节公共扣除；
- 四条有优先级、默认路线和独占名称的累计结局；
- 十三维批次指纹。

蓝图阶段的 `players[].chapterActions` 和 `chapterBeats` 必须为空。

## 第二阶段：章节装配

第二阶段只负责把蓝图变成真正可运行的五章因果链：

- 每名玩家至少覆盖 `ceil(chapterCount × 0.6)` 个不同章节；
- 每章必须包含具体动作对象，不能只写“调查、质问、交换、隐瞒”；
- 章节机制文本必须明确“触发、判定、成功、失败”；
- 状态读写、证据开关、资源增减、权限变化必须被下游章节或结局真实读取；
- 状态读取失败必须进入可执行替代分支，并明确额外代价；
- 玩家可见选择只能写世界内行为；隐藏变化统一放在 `options[].effects`，一个选择可同时影响状态、资源、证据或事件；不得出现 `state-`、`写入状态`、`verified` 等实现词；
- number 全程使用 JSON 数字，enum 全程使用允许字符串，boolean 全程使用布尔值；
- 同一概念不能同时注册为 state 和 resource，防止双重扣除；
- 资源只能挂在执行具体行为的选项或有条件失败代价上；同一决策必须保留至少一个不消耗该资源的真实替代选项；
- 聚光章分布、角色贡献和结局因果路径必须成立。

## 严格机械验收检查什么

机械验收不是“写完后替 AI 设计故事”，只判断可以确定计算的事实：

- 姓名、key、类型、引用是否一致；
- 玩家是否被重复登记为 NPC；
- 核心责任是否真正属于 cause/escalation/maintenance，而不是把受害者或解决者改名为责任人；
- 六人行动章节覆盖是否达标；
- 贡献类型是否过度集中在 evidence；
- 证据是否来自真正独立的 provenanceGroup；
- provenanceGroup 是否为真实人物、机构、系统、设备或物件，而不是“来源01-1”包装壳；sourceType 与实体 type 是否语义相容；
- 状态是否先登记、后写入、再读取，类型是否一致；
- 状态是否只描述一个主体的一个判断维度；事实、授权效力、条款适用、结果承认和行动资格不得混成同一状态；
- 结局是否在同一条完整分支路径上可达、互斥、有优先级并读取前后章节状态；
- 资源是否真实使用，是否被重复建模；
- 是否重新退化为通用“决策容量”；
- 机制是否有触发、判定、成功和失败；
- 文风是否逐章落地；
- 是否出现万能信任值、通用结局名或批量模板行动；
- 十三维批次指纹、人物名、结局名是否重复或高度近似。
- 玩家姓名是否共享固定中间字、循环六个尾字或在整批中过度统一长度；
- 状态条件与结局文案是否命中已声明的语义冲突；高风险篇目的时间线和规则不变量是否被破坏。
- 授权用途是否越界，事件声称的授权状态是否与授权范围一致；
- 每个责任类型是否与具体玩家、具体事件成对绑定，而不是两组数组互相猜测；
- 世界规则是否在声明的章节、前置条件同时成立时才执行；派生状态是否只由对应规则产生；
- 证据是否真的来自不同原始根、不同共同故障域和不同独立域，而非同一服务器的日志与镜像冒充双源；
- 数字材料的取证方法是否与对象相容，例如禁止对服务器镜像使用磁粉检测。

“高概念解释是否足够惊艳”“人物是否像活人”“笑点是否好笑”仍属于创作合同和人工编辑判断，程序不能伪装成审美裁判。

## 失败策略

默认每篇只创建一份完整草稿。蓝图阶段和章节装配阶段可各自在同一创作合同下从空响应重试，装配重试会复用已经验收的蓝图，但不会读取失败装配稿；只有显式提高 `OUTLINE_FULL_DRAFT_ATTEMPTS` 才会从蓝图开始创建另一份完整草稿。以下情况会触发本阶段重试或整份拒收：

- 网络或 SSE 中断；
- 输出截断或 JSON 无法解析；
- 蓝图合同不合格；
- 章节装配擅自修改蓝图；
- 任一机械硬门禁失败。

失败稿和阶段流仍写入 checkpoint，便于定位问题，但不会作为下一份草稿的 patch 基底。

## 流式、断点与并发

V2.4 的蓝图与章节装配都使用 DeepSeek SSE 流。四十篇之间仍可高并发，但同一篇内部采用“蓝图 → 联合章节装配”的顺序：玩家行动必须引用真实存在的 `decision.key` 和 `optionKeys`，章节选择也必须与行动后果一致，所以不能再把玩家行动与章节决策分给两个互相看不见的并行请求。V2.3 的三个并发组件只保留为旧协议兼容路径，不用于 V2.4。

这仍然不是写完后的三轮创意审稿：第一阶段制定创作结构，第二阶段让结构运行；程序只做确定性的合同验收。服务端持续保存：

```text
checkpoints/<编号>.<会话ID>.draft-<次数>.blueprint.partial.json
checkpoints/<编号>.<会话ID>.draft-<次数>.blueprint.status.json
checkpoints/<编号>.<会话ID>.draft-<次数>.blueprint.attempt-<次数>.partial.json
checkpoints/<编号>.<会话ID>.draft-<次数>.blueprint.attempt-<次数>.status.json
checkpoints/<编号>.<会话ID>.draft-<次数>.assembly.partial.json
checkpoints/<编号>.<会话ID>.draft-<次数>.assembly.status.json
checkpoints/<编号>.<会话ID>.draft-<次数>.assembly.attempt-<次数>.partial.json
checkpoints/<编号>.<会话ID>.draft-<次数>.assembly.attempt-<次数>.status.json
checkpoints/<编号>.<会话ID>.draft-<次数>.assembly-player-actions.*.json
checkpoints/<编号>.<会话ID>.draft-<次数>.assembly-chapter-beats.*.json
checkpoints/<编号>.<会话ID>.draft-<次数>.assembly-style-expressions.*.json
```

每篇通过后立即写入 `items/<编号>.json` 并重建 Markdown 汇总。

默认并发数为 10：

```powershell
$env:OUTLINE_BATCH_CONCURRENCY = "10"
$env:OUTLINE_FULL_DRAFT_ATTEMPTS = "1"
$env:OUTLINE_BLUEPRINT_ATTEMPTS = "3"
$env:OUTLINE_ASSEMBLY_ATTEMPTS = "3"
$env:OUTLINE_REQUEST_TIMEOUT_MS = "240000"
npm run generate:forty-outlines
```

若某篇已经有经当前最新版校验仍然有效的 accepted blueprint，只想继续装配而不重复消耗蓝图调用，可显式开启：

```powershell
$env:OUTLINE_REUSE_ACCEPTED_BLUEPRINT = "1"
```

脚本会重新用当前 brief、spec 和 V2.4 门禁验证旧蓝图；只有仍然通过才复用，并把它复制到本次会话检查点。旧 V2.3 蓝图不会被伪装成 V2.4 继续装配，不能把旧蓝图的玩家行动嫁接到新蓝图。

单篇试跑可使用：

```powershell
$env:OUTLINE_ONLY_IDS = "14"
$env:OUTLINE_BATCH_CONCURRENCY = "1"
npm run generate:forty-outlines
```

## 2026-08-01 V2.4 机制修订

V2.4 针对的不是某一篇故事的字面错误，而是上一版暴露出的系统性漏洞：结构合格不代表事实一致，单项值可达不代表结局能在同一路径命中，不同来源名称也不代表真正独立。

本版新增以下创作结构：

- `semanticConstitution.facts`：以稳定 key 锁定主体、谓词、对象、真假、作用范围、有效时间和支持证据，人物秘密、时间线、状态与结局不能再各写一套事实；
- 玩家 `coreSecret` 必须通过 `secretFactKeys` 引用宪章事实；涉及授权时还要通过 `authorizationGrantKeys` 引用具体授权记录，避免人物秘密与幕后真相对同一授权给出相反说法；
- `authorizationGrants`：明确授权人、被授权人、资产、允许用途、禁止用途和有效期，区分“凭证是真的”和“用途越权”；
- `branchEvents`：单独登记可由玩家选项或规则触发的条件事件；`causalTimeline` 只保存已经发生的事实，避免章节选择把过去事件“再次触发”；
- `worldRules`：每条规则声明 `evaluationChapterKey`、触发事件、前置条件、授权主体、效果、审计证据与失败方式；运行器会在完整分支中执行规则，不只检查字段存在；
- 原子状态：每个状态登记 `subjectKey + dimension + controlMode`，将真实性、完整性、授权效力、条款适用、结果承认、参赛资格等拆开；`derived` 状态只能由 `derivedByRuleKey` 指向的规则写入；
- 逐人责任映射：`causalTimeline[].actorResponsibilities` 直接记录“哪个玩家在该事件承担哪类责任”，避免多行动者与多责任类型的笛卡尔歧义；
- 因果参数连续性：同一 `targetKey + parameterKey` 被多人先后修改时，后一事件的 `beforeValue` 必须等于前一事件的 `afterValue`，从结构上区分谁改了启动条件、谁改了策略参数、谁只是污染证据；
- 证据来源根：除 `provenanceGroup` 外登记 `originRootKeys`、`commonCauseKeys`、`independenceDomain`、`methodDomain`、`methodOperation` 和 `artifactProduced`；同一服务器生成的日志与镜像会被识别为同根材料；
- 联合分支执行：按章节依次执行入口条件、失败替代、公共效果、玩家选项与世界规则，再检查一条结局的全部条件能否在同一快照成立；
- 选择内资源：删除 V2.4 的 `resourceUsagePlans` 公共必扣合同，改用 `resourcePolicies`；消耗放在 `chapterBeats.decision.options[].effects`，并强制保留不消耗资源的真实选择；
- 分层就绪结果：通过时分别标记事实一致、分支一致、来源独立、责任完整、领域方法相容和世界规则完整，不能再用一个 `structuralValidationPassed` 冒充全部质量结论。

《决赛第五局》的批次合同也不再依赖单个“是否认可模拟赛”状态，而是拆分比赛真实性、比赛完整性、授权效力、条款适用、结果承认、阵容资格、医疗许可和冠军主张。官方服务器日志与服务器镜像明确登记为同一来源根，并增加对手方遥测作为独立根。该合同只证明生成前机制已经修正，不代表新大纲已经完成生成或人工审稿。

V2.4 的目标目录是 `examples/pending-review/四十题材大纲-V2.4语义宪章版-20260801`。当前完成的是 40 篇合同预检，不应把尚未重新生成的 V2.3 内容复制进该目录冒充 V2.4 结果。

## 2026-08-01 V2.3 修订结论（历史）

V2.2 的 40 篇结果暴露出“讨好校验器”问题：固定中间字与六尾字姓名矩阵、玩家选项直接操作内部状态、`source-*` 来源壳、受害者被称为核心责任人、通用 `decision-capacity` 资源、实体名称与 type 语义冲突，以及合法状态值与结局内容互相矛盾。

V2.3 已完成以下修订：

- 删除 V2.3 路径中的创意后处理；装配器只合并 AI 原始数组，不补写选项、状态、资源、来源或失败分支；
- 240 个姓名改为逐题策划，并增加共享中间字、六尾字签名、尾字高频和长度过度统一门禁；
- 玩家可见 `choiceText` 与隐藏 `sets` 分离；
- 来源实体拒绝壳命名，并检查 `sourceType ↔ entity.type` 语义对应；
- 增加四类责任、严格因果时间线、状态值世界语义和题材语义不变量；
- 16 个需要数值资源的题材全部使用世界内资源合同；
- 《决赛第五局》整体重构为双方正式数字孪生已经在官方隔离服务器实时完成的代理赛，不再使用预测未来录像解释；
- Markdown 审查稿分开展示公共必然效果、成功分支、失败分支、各选项隐藏映射和章节出口状态。
- 每次蓝图/装配失败的原始流式结果和拒绝原因单独归档；下一次生成会收到上一轮失败项，但必须重写当前阶段，不允许后端定点改写创意字段；
- 任意长度门槛不再代替语义质量：责任行动允许简洁表达，但必须有具体动词、对象和因果事实；mystery 不再机械要求六人各持一条证据，只要求至少四条可操作证据与真正独立的双源结论；
- 实体语义判断优先依据实体名称，避免把“职责中提到服务器”的技术官误判成系统；状态不变量改为验证明确世界事实，避免禁止词命中“不会自动判胜”等否定句。
- 对确实需要数值资源的题材，生成前合同预分配三个资源变化章节；AI 必须把世界内消耗写在对应章节的公共效果中，失败分支不得重复扣减，防止为了满足“每章有代价”把同一资源十次扣成负数。
- 将单个超大 assembly JSON 拆成三个并发流：玩家行动只处理角色章节贡献，章节节点只处理状态、选项、资源和失败分支，文风组件只处理逐章表现。三个原始组件分别通过技术合同后合并，后端不改写其中的创意字段。
- 并发组件使用逐项验收而不是“一个失败、全部作废”：同轮返回的合格组件立即进入检查点，只有失败组件消耗自己的重试次数；总校验的问题按玩家、章节、文风准确路由。
- 资源轨迹区分公共必然效果与条件失败代价：公共 `resourceDeltas` 每次必须执行，不能在可达性计算中被当成可跳过选项。蓝图提示会预先给出按 `resourceUsagePlans` 计算的终局资源值，结局资源条件必须能由该终值满足。
- 玩家行动也使用逐角色逐章骨架：固定行动章节、结局状态写入、空的个人资源/证据开关和蓝图既有关系对象在同一行给出，避免模型跨表漏抄后再“讨好”总校验。
- 创作文本与内部结构彻底分层：`hookPromises`、结局标题/内容和玩家可见选择不得出现 `state-`、`resource-`、`chapter-`、`role-` 或内部枚举；这些 key 只能留在结构化引用字段。
- 对需要严格身份边界的题材，可在批次合同逐席位锁定玩家身份。第 32 篇六名玩家固定为同一战队的数据官、主力、领队、替补、战术教练和经理；赛事监督、对手与联盟人员只能作为外部实体。
- 关键证据允许预分配真实世界来源，但禁止来源壳。第 32 篇四个来源分别是官方隔离服务器、紧急连续竞赛条款原件、赛事监督和第五局服务器镜像，并锁定为设备日志、制度记录、独立证词、物理检验。

旧 V2.2 与 V2.3 批次只保留为压力测试和回归语料，不能再标记为“可直接进入扩写”。当前目标已经切换到上文的 V2.4 目录。

V2.3 代表性样本《决赛第五局》曾通过当时的结构门禁，也正是它进一步暴露了授权事实冲突、同一状态承担多个判断、同源证据冒充独立来源、资源被公共效果强制耗尽和行动链提前决定结局等问题。它不能作为 V2.4 合格样本继续使用。

V2.4 当前只完成合同与代码层预检，不代表四十篇批次已经生成或跨篇多样性已经验收。Markdown 在只跑 `OUTLINE_ONLY_IDS` 时必须明确标为“试跑汇总”，完整 40 篇未跑齐前不得显示“四十篇跨篇门禁通过”。

## 人工编辑仍然负责什么

机械通过只代表“结构、类型、引用和因果最低标准合格”，不等于可以直接出版。人工编辑仍需判断：

- 钩子兑现的惊奇强度；
- 人物是否可信而非字段齐全；
- 动机与专业流程是否符合现实；
- 文风、对白、喜剧或情感效果；
- 同题材作品之间更深层的语义同构。

因此最终状态应明确区分：

- `strictMechanicalValidationRun: true`
- `creativeEditorialAuditRun: false/true`

不能再把“未执行严格审稿”误写成“已按 V2.2/V2.3/V2.4 合格生成”。
