# 织幕产品与品牌维护总控台

最后更新：2026-07-30
维护范围：产品定位、品牌口径、视觉原则、前端体验、宣发内容与文档一致性
当前阶段：可信 Beta；适合小规模真实团队试用与人工陪跑，不对外承诺大规模商用能力

> 本页是产品与品牌工作的当前总控入口。工程成熟度以 [项目状态](./PROJECT_STATUS.md) 和 [产品状态](./PRODUCT_STATUS_ZH.md) 为准；带日期的竞品研究、体验审计与活动材料是快照，不覆盖当前事实。

## 1. 当前产品判断

织幕已经具备创作、开房、主持、玩家体验、存档和复盘的真实闭环。现阶段最主要的问题不是功能数量，而是三件事：

1. 产品能力没有完全收束成陌生创作者能自然理解的一条主流程。
2. 官网、创意提案、产品内文案与工程状态存在口径和视觉漂移。
3. 缺少真实试点案例，导致宣发仍主要依靠功能说明，可信度和转化力不足。

因此，下一阶段的产品重点不是继续堆功能，而是把“导入一份现有剧本并跑完第一场测试”做成可理解、可完成、可复盘的代表性体验。

## 2. 品牌基线

### 2.1 品牌角色

织幕不是替作者自动写完故事的生成器，也不是以战棋地图和掷骰为中心的通用 VTT。织幕更适合被定义为：

> **长线互动叙事的创作与运行平台。**

它连接创作完成后的关键断层：剧本如何按角色权限发布、如何开出互不污染的平行房、如何让主持掌控现场、如何把真实运行问题回写到下一版内容。

### 2.2 优先服务对象

| 顺位 | 人群 | 当前最强需求 | 织幕应提供的第一价值 |
|---|---|---|---|
| 1 | 已有母稿的独立作者、小型工作室 | 把 Word/PDF/飞书稿件变成可测试的线上体验 | 导入、结构检查、创建测试房 |
| 2 | 同时承担主持工作的创作者 | 减少线索、进度、规则和现场状态的手工对账 | 主持台、自动化、审计与恢复 |
| 3 | 专职主持人 / GM | 稳定运行长线或多房内容 | 当前幕指引、关键节点控制、卡关处理 |
| 4 | 受邀玩家 | 快速入房并沉浸阅读、探索和收线索 | 角色视角、权限隔离、实时同步 |

Beta 阶段不应同时把四类人都当成官网的同等购买者。首页主叙事优先面向“已有剧本、准备开第一场测试”的作者或工作室；主持人与玩家是证明这套系统能真正运行起来的第二、第三视角。

### 2.3 对外一句话

主标题：

> **把一个剧本，运行成一场真正同步的故事。**

解释句：

> 创作者组织角色与线索，主持人掌控现场节奏，玩家只看到此刻该知道的内容；每次运行都可追踪、可恢复、可复盘。

短版定位：

> **织幕，让剧本从写完走到真正跑起来。**

### 2.4 四个稳定记忆点

1. **从母稿到首场**：支持已有稿件导入、结构确认、测试房和首场运行。
2. **三端同一事实源**：创作者、主持人、玩家使用同一份故事数据，但看到正确的不同视角。
3. **一份剧本，多次稳定运行**：模板与运行房分离，平行房之间的进度、线索和结局互不污染。
4. **运行结果回到改本**：阅读、线索、主持操作和复盘数据成为下一版修改依据。

## 3. 当前可说与不可说

### 3.1 已有证据支持

- Creator、Host、Player、Site 四端已经成形。
- 创作内容与房间运行实例分离。
- 角色视角、私人分幕、线索和运行状态具备权限边界。
- 平行房、实时事件、主持干预、checkpoint 和复盘链路已存在。
- TXT、Markdown、DOCX、PDF 等稿件导入路径已有产品与服务基础。
- 当前适合可信 Beta 和少量人工陪跑试点。

### 3.2 对外发布前必须复核

- 任意测试数、迁移数、路由数、完成率或性能数字。
- “无限平行房”“完全自动主持”“秒级永不掉线”等绝对承诺。
- “大规模商用 SaaS 已完成”或标准 SLA 已可兑现。
- 未经真实试点确认的案例、推荐语、效率提升比例和商业收益。
- “AI 一键生成完整高质量剧本”等会削弱作者主权、且缺乏稳定质量证据的说法。

所有易变化数字只从 [`GENERATED_PROJECT_STATUS.json`](./GENERATED_PROJECT_STATUS.json) 和同一提交的验收工件读取；创意提案不得继续长期硬编码历史数字。

## 4. 视觉与构图原则

### 4.1 已确立的品牌气质

当前官网与产品端形成了较清晰的“东方编辑部 / 剧本工作室”气质：

- 米白纸张为主背景，墨绿承担结构与行动，铜金承担标记和强调。
- 标题使用中文衬线体，正文和操作使用无衬线体。
- 卡片圆角克制、阴影轻、分隔线清晰，避免娱乐 App 式高饱和堆叠。
- 真实产品截图优先于抽象插画、科技光效和虚构概念图。

该方向应作为唯一品牌基线。早期创意提案的黑金科技风可以保留为历史比赛快照，但新宣发材料应回到当前纸张、墨绿、铜金体系。

### 4.2 页面构图规则

1. 首屏只完成一个任务：说明“给谁、解决什么、下一步做什么”。
2. 每屏最多保留一个主行动；次行动不得与主行动同权重。
3. 产品截图必须配一句“用户在这里完成什么”，不能只当装饰。
4. 桌面端优先使用“叙事解释 40% + 产品证据 60%”；移动端先价值、再行动、再截图。
5. 错误、演示、未登录、空状态不得连续出现三条相似提示。
6. 产品术语优先使用“剧本、角色、分幕、线索、运行房、复盘”；`world`、`segment`、`SSE`、`checkpoint` 等工程词只进入高级说明。

### 4.3 前端状态质量线

每个核心页面必须同时设计并验收：

| 状态 | 必须回答 |
|---|---|
| 首次进入 | 我在哪里？我现在能做什么？ |
| 未登录 | 为什么要登录？登录后会得到什么？ |
| 空状态 | 为什么是空的？最推荐的下一步是什么？ |
| 加载 | 正在加载什么？是否可以先做别的？ |
| 降级 / 断线 | 哪些能力不可用？数据是否安全？如何恢复？ |
| 成功 | 刚刚发生了什么？下一步去哪？ |

错误信息不得直接展示 `[object Object]`、原始状态码或无法执行的工程建议。

## 5. 首轮产品优先级

### P0：立即修正

| 问题 | 当前证据 | 完成标准 |
|---|---|---|
| Host 错误对象直接显示为 `[object Object] (502)` | [体验审计](./PRODUCT_EXPERIENCE_AUDIT_2026-07-30_ZH.md) Step 8 | 错误转换为用户可理解的信息，并提供明确恢复动作 |
| Creator 降级状态重复显示多条连接异常、演示提示和登录入口 | 审计 Step 6 | 合并为一个持久状态条 + 一个主要恢复动作 |
| 创意提案硬编码过期工程数字 | 审计 Step 10 | 改为可复核当前数字，或使用不易过期的能力证明 |
| 对外视觉分裂 | 官网浅色编辑部 vs 创意提案黑金科技 | 新物料统一使用当前品牌 tokens、字体和截图规则 |

### P1：本版本内收束

| 问题 | 产品动作 |
|---|---|
| 移动端菜单缺少登录 / 开始创作 | 在菜单底部加入固定主 CTA，并保留玩家/主持入口 |
| Creator 首次使用仍像工具集合 | 以“立项 → 真相 → 内容 → 互动 → 运行 → 测试 → 发布与复盘”作为唯一主流程 |
| 官网主 CTA 对已有稿件用户不够具体 | 测试“导入我的剧本，跑首场测试”对比“开始创作” |
| 缺少可信案例 | 完成至少 1 个可授权、可脱敏、可截图的真实 pilot case |
| 三端入口文案不完全一致 | 统一角色名称、登录状态、跨端跳转与当前端标识 |

### P2：需要真实使用验证

- 首场测试从注册到复盘的完成率与中断点。
- 主持人在一场运行中离开织幕去群聊、表格或文档的次数。
- 创作者能否从复盘直接定位下一版修改对象。
- “长线剧本杀”“互动叙事”“跑团”三种说法中，哪一个带来最高质量试点线索。

## 6. 宣发内容主轴

内容不按功能目录展开，按用户从“有一份稿”到“跑完一场”的变化展开：

1. 一份 Word 剧本，怎样变成可选角、可发线索的测试房。
2. 主持人怎样不用群聊手动记每个人拿到了什么。
3. 同一份剧本怎样开多个互不污染的平行房。
4. 跑完一场后，怎样知道下一版具体该改哪一幕、哪条线索。
5. AI 怎样作为检查和辅助，而不是替作者决定故事。

详细竞品与宣发建议见 [竞品定位与宣发简报](./COMPETITIVE_PROMOTION_BRIEF_2026-07-30_ZH.md)。

## 7. 文档维护机制

### 7.1 更新触发器

| 发生变化 | 必须同步 |
|---|---|
| 定位、优先用户、主 CTA、品牌语气 | 本页、官网、创意提案、报名帖 |
| 页面流程、导航、术语或关键空状态 | 本页、产品功能总览、对应端 README / 指南 |
| 产品成熟度、发布证据或风险 | `PROJECT_STATUS.md`、`PRODUCT_STATUS_ZH.md` |
| 新竞品、新市场变化或新用户反馈 | 新建带日期的研究快照；只有稳定结论再回写本页 |
| 新试点案例 | Pilot 记录、案例授权、官网案例和宣发素材 |
| 易变化工程数字 | 生成状态文件；禁止手工复制到长期物料 |

### 7.2 每次文档更新的最小检查

```powershell
npm run status:generate
npm run docs:index
npm run check:docs
```

### 7.3 每周产品维护清单

- 核对本页 P0/P1 状态，不用“已规划”替代“已上线”。
- 抽查官网、Creator、Host、Player 的首屏、空状态、错误状态和移动端。
- 从反馈、支持记录和试点复盘中提炼最多三个新问题。
- 检查所有对外数字、截图、案例和套餐是否仍有证据。
- 只把跨两次迭代仍成立的结论提升为品牌或产品原则。
